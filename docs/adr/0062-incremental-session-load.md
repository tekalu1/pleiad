# 0062 loadSession を、持っている履歴の続きだけにする

- 状態: 提案

## 状況

ターンが終わるたびと、つなぎ直すたび（スマホは背面から戻るたびに線が切れる）に、画面は会話の履歴を全量で読み直していた（`syncHistory`・静かな読み直しの `loadSession`）。2000 発言の会話は 5.2M 字、実データの最大の会話は提示（Visualize の HTML の写し）込みで 4M 字になる。中継（往復 100ms・10Mbps）では 1 回 6 秒、300ms・5Mbps では 13 秒で、中継の線は 1 本の暗号化チャネルなので、その間は次のコマンドや出来事も待たされる。読み直した後は DOM も全部作り直していた（issue #37）。

読み直しのほとんどは、末尾に数件増えただけで、先頭は変わらない。ただし途中の発言が書き換わる会話がある（圧縮・Codex の履歴の書き換え・枝の切り替え・ツールの結果が後から付く・添付が発言に結ばれる）。

## 決定

1. `loadSession` に引数 `from`・`check`・`presentFrom`・`presentCheck` を足す（`core/protocol.mjs` の `COMMANDS` は変えない。`PROTOCOL_VERSION` も据え置く）。
   - 画面は、持っている発言の先頭（末尾の 2 件を除く）と、持っている提示の全部の署名の並びの値を `check`・`presentCheck` として送る。署名は `web/history-sync.mjs` の `messageSig`・`presentSig`（JSON の署名。提示は中身の長さだけを見る）。
   - サーバーは、同じ計算で先頭が合い、件数が足りているときだけ、`messages` を `from` 以降、`presents` を `presentFrom` 以降に切り、`from`・`total`・`presentFrom`・`presentTotal` を足して返す。合わない・頼みが壊れている・頼みが無いときは、今までどおり全量を返す（`from` の印が無い）。
   - 画面は印があり、頼んだ位置と件数が合うときだけ、持っている先頭につないで全量の形にする。合わなければ全量を取り直す。呼び出し側が受け取る形は、差分でも全量でも同じ。
   - 使うのはターン終了の `syncHistory` と静かな読み直し。会話を開くとき・枝の切り替え・`outline`（系譜の照合）は全量のまま。
2. 静かな読み直しでは、DOM も残す。今描いてある行と読み直した履歴を、描く行の並びで先頭から比べ、最初に違う項目から後ろだけ描き直す。比べるのは発言全体の署名で、ツールの結果・圧縮の区切り・提示の結び付きが変わった場合も「違う」になる。読み返していた位置は基準の行で保つ。

## 理由

- 署名の一致を確かめるので、途中が書き換わった会話でも、古い先頭に新しい続きをつなぐことはない。合わなければ全量に戻るだけで、遅くなる以外の害がない（最悪でも今と同じ）。
- 提示は 1 件が 1MB を超えることがあり、実データでは全量の 4 割を占めた。発言だけを差分にしても、毎ターン提示の全部を送り直すことになるので、提示も同じ仕組みに載せる。提示は末尾を取り直さない（署名が合わなければ全量）。
- 引数を足すだけなので、古い画面（引数を送らない）にも、古いサーバー（引数を知らず全量を返す）にも壊れない。
- 採らなかった案: 会話ごとの版番号（履歴は Claude の transcript・Codex の rollout など外部のファイルで、Pleiad が版を持てない）、発言の uuid だけでの照合（Claude は複製した発言に新しい uuid を振る。ツールの結果の変更を拾えない）、`total` と最後の発言だけの照合（途中の書き換えを見逃す）。

## 影響

- サーバーは差分の応答でも履歴の全量を読む（外部のファイルを読み直す費用は変わらない）。画面が送る先頭の署名の確認にも、全量の署名の計算がかかる（2000 発言で数十 ms）。減るのは転送・受け取り側の JSON の読み込み・描き直し。
- 画面は初めて頼むときに、持っている全発言の署名を計算する（1 度だけ。以後は要素ごとに覚える）。
- ページングなど、開くときの量を減らす変更（issue #37 の段階 3 以降）はこの ADR の範囲外。
- 仕様の今の形は `docs/design.md`「会話の読み直し」。
