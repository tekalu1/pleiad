# 0001 決定を ADR に残す

- 状態: 承認（2026-09-26）

## 状況

決定の理由が design.md・design-system.md・各機能の docs の本文、調査メモ、承認済みのモックに散っていた。本文は「今の形」と「なぜそうしたか」が混ざって長くなり、モックは承認の記録を兼ねていたため、モックを消すと承認の跡も消える（0002）。

## 決定

- **living doc（design.md・design-system.md・各機能の docs）は今の形**を書く。変わったら書き換える。
- **ADR はなぜそう決めたか**を書く。`docs/adr/NNNN-<英小文字とハイフンの題>.md`。番号は 4 桁の通し番号で、欠番を作らない。一覧は置かない。
- 書式は「状態」の行と、状況・決定・理由・影響の 4 節。置き換えの関係があるときだけ `- 置き換えた: NNNN` / `- 置き換えられた: NNNN` の行を足す。1 決定 1 ファイル、60 行程度まで。
- 状態は `提案` → `承認（日付）` → `置換（NNNN）`。採らなかったものは `却下`（理由 1 行）として残す。
- `承認` にするのはユーザーだけ。ユーザーが会話で承認したら、エージェントが状態の行を書き換えてコミットする。過去にモックで承認された決定は、当時の日付で `承認（日付）` と書く。
- `提案` の ADR も main に入れてよい。状態で区別する。
- `承認` の後は本文を書き換えない（誤字・状態の行・置換先の行だけ）。変えるときは新しい ADR を書き、古い ADR を `置換（NNNN）` にし、living doc を書き換える。
- ADR にはモック・スクリーンショット・調査メモへのリンクを貼らない（`temporary/` は追跡されない）。決まった形は文章で書く。

## 理由

- 本文を「今の形」だけにすると、読む人（人間もエージェントも）が今の規則を早く掴める（design-system.md §2.7 を文書にも効かせる）。
- 理由を書き換えずに残すと、後から「なぜこうなっている」に答えられ、同じ議論をやり直さずに済む。
- 採らなかった案: 決定を design.md の「決めたこと」に積み続ける（本文が変更記録になって長くなる）、モックを承認の記録として残し続ける（0002 で追跡をやめた）。

## ADR が要るとき

- 元に戻すのが高くつく決定（データの正本・プロトコル・保存形式・外部との接続）
- 安全・権限に関わる決定
- design.md の「思想」「やらない」を変える決定
- ユーザーが承認した UI の案のうち、理由を残す価値があるもの
- 開発・運用の決まり

要らないもの: 決定を伴わない実装と修正、既存の規則の範囲内の画面の手直し、調査の経過（`temporary/reports/`）。

## 影響

- living doc からは `（ADR NNNN）` で ADR を指し、ADR からは living doc の節を指す。
- AGENTS.md の「決定の記録（ADR）」にこの要点を置く。
