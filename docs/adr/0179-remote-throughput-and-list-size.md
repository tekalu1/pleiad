# 0179 リモートの流量と送る量: 受け手が窓を広げ、大きい返事は WS の外で gzip にし、一覧は細くして差分で送る

- 状態: 提案
- 日付: 2026-10-09
- 関連: [ADR 0013](0013-remote-via-relay-with-noise.md)（中継と Noise のチャネル）、[ADR 0144](0144-ios-remote-core-in-swift.md)（iOS の端末側の Swift）、[ADR 0083](0083-control-surface-cli.md)（操作 `core/ops`）、docs/remote.md §4.2・§4.3

## 状況

中継越しの画面（スマホの殻・デスクトップ版の端末）で、会話の一覧が遅かった。実データの写し（会話 2,150 件）を、往復 0/100/300 ms・20 Mbps の線で測ると次のとおりだった。

- 一覧（WS の `listSessions`）は 1 回 2.75 MB。届くまで 1.25 / 2.11 / 4.18 秒で、往復が延びるほど遅くなる。流量の窓（ストリーム 256 KiB・チャネル 1 MiB）が、帯域と遅延の積（往復 300 ms・20 Mbps で約 0.75 MB）より狭く、往復ごとに窓の分しか送れない。
- WS は 1 本のストリームに全部乗る。一覧の後ろに並んだ小さい返事（`listStatuses`）は、一覧を送り終わるまで待たされた（1.19 / 2.05 / 4.12 秒）。
- 一覧の 42% は振り分けの記録（`routing`）、0.19 MB は委譲の記録（`delegation`）の詳しい中身だった。どちらも画面は一覧の行から読まない（委譲カード・バックグラウンドの一覧はタスクの行 `agentTasks` / `delegation.tasks` を読む）。
- 画面は会話が動くたびに一覧を全部取り直す。

## 決定

1. **D1 受け手が窓を広げる。** 取り決めの初期窓（ストリーム 256 KiB・チャネル 1 MiB）は変えない。受け手は HELLO の直後にチャネルへ、ストリームを開いた直後（端末は HTTP_REQ / WS_OPEN を送った直後、ホストは受け付けた直後）にそのストリームへ、WINDOW の足し増しを送り、ストリーム 1 MiB・チャネル 4 MiB に広げる。ホスト（`core/remote/channel.mjs`）・Node の端末（同じ実装）・Android（Kotlin）・iOS（Swift）の 4 つで同じにする。
   - 交渉はしない。WINDOW は前からある「増分を足す」フレームなので、古い相手はそれを受けて多めに送るだけで、古い相手が窓を広げなければ今までの窓で送る。版の組み合わせ（古いアプリ×新しいホスト・その逆）を問わない。中継はフレームの中身を見ないので、中継の版も問わない。
   - ストリーム 1 MiB は往復 300 ms・20 Mbps の積（約 0.75 MB）を 1 本で満たす大きさ。それより広げると、大きい返事の後ろに並ぶ小さい返事の待ち（窓 ÷ 帯域。1 MiB で 20 Mbps なら約 0.4 秒）が延びるので広げない。
   - チャネル 4 MiB は、中継が相手側に溜めてよい量（8 MiB。§5.3）の半分。受け手が抱えるのも最大 4 MiB で、端末のメモリに収まる。
2. **D2 大きい返事は WS の外に置き、HTTP で取る。** 画面が `bulk: true` を添えたコマンドの返事が 64 KiB 以上で、つなぎ先がこの PC でない（`isLocalRequest` が偽。中継越しの接続口は `x-forwarded-for: pleiad-remote` を付ける）とき、サーバーは返事の本文を `/bulk/<32 桁の 16 進>` に置き、WS には `{ kind: 'response', id, ok: true, bulk: '/bulk/<id>' }` だけを返す。画面はそれを `fetch` で取り、`result` と同じに扱う（`web/client.mjs`）。実装は `core/bulk-replies.mjs`。
   - HTTP の要求はチャネルの別のストリームになる。チャネルはストリームごとに 1 フレームずつ順に送る（`_pump`）ので、大きい返事の HTTP と WS の小さい返事が交互に流れ、小さい返事は大きい返事の後ろに並ばない。
   - WS のメッセージの順序は変えない（WS には相変わらず 1 通ずつ順に返し、その 1 通が置き場の URL になるだけ）。返事を待つ側は id で受けるので、本文が後から届いても他のコマンドの順に影響しない。
   - 置き場は GET だけ・1 回取ったら消える・60 秒で消える・合計 64 MiB まで（超えたら古いものから消し、1 つで上限を超えるものは置かずに WS で返す）。トークン（Cookie か `?token=`）が要るのは他の HTTP と同じ。`cache-control: private, no-store`。
   - `accept-encoding` に gzip があれば gzip（水準 6）で返す。端末の代理（Node・Kotlin・Swift）はどれも `content-encoding` を素通しする。2,150 件の一覧 1.56 MB は 109 KB（約 1/14）になり、gzip にかかるのは 14 ms。
   - この PC の画面（ループバック）には置かない（WS で返す方が速い）。
3. **D3 WS のメッセージの圧縮（permessage-deflate）は見送る。** ホストの接続口（`core/remote/forward.mjs`）は WS をフレームのまま通さず、メッセージに組み立て直してローカルのサーバーへ渡す。端点の画面とサーバーの間で拡張を交渉しても、圧縮されるのはループバックと端末の中だけで、中継の線は平文の大きさのまま流れる。線の上で縮めるには、チャネルに「圧縮した WS_MSG」の印を足し、Node・Kotlin・Swift の 4 つの端で交渉と伸長を作ることになる。一方で、線に流れる大きい返事は一覧と会話の読み込みで、一覧は D2 の gzip で約 1/14 になり、2 回目からは差分（E1）で数十〜数百バイトになる。会話の返事を小さくするのは別の作業（会話の段階的な読み込み）で進んでいる。費用に見合わない。
4. **E1 画面の一覧を細くし、変わった行だけ送る。**
   - WS の `listSessions` の行から `routing` を外し、`delegation` は依頼元（`parentSessionId`）と、端末の AI から任された印（`remote`）だけにする（`core/session-list-delta.mjs` の `slimRow`）。画面が一覧の行から読むのはこの 2 つだけ。振り分けの詳しい中身・タスクの id は、要る画面がタスクの口（`agentTasks`・`delegation.tasks`・`delegation.status`）で取る（今もそうしている）。
   - **操作（`core/ops` の `sessions.list`）は変えない。** MCP・CLI・`invoke` は今までどおり詳しい中身を受ける。変えるのは画面の WS の `listSessions` の返し方だけなので、OPS_UPDATE_SNAPSHOT は要らない。
   - 画面が `delta: true` を添えると、返事は `{ seq, full: true, rows }`。次から `since: <前の seq>` を添えると、`{ seq, full: false, rows: 変わった・新しい行, removed: 消えた行の id, front?: [...] | order?: [...] }` を返す。サーバーは接続ごとに、送った一覧の写し（行の順と、行ごとの中身の指紋）を新しい順に 4 つ持つ。写しが無い（つなぎ直した・古すぎる・ホストが起動し直した）なら全部を返す。
   - 並びの直しは、`front`（先頭に上がった行。残りは前の並びのまま）で足りればそれだけ、足りなければ並び全部（`order`）を送る。会話が動くと先頭に上がるので、ふつうは `front` の 1 行で済む。
   - 画面の受け手（`web/session-list-sync.mjs`）は写しに当てて並びを組み立て、組み立てられない（行が欠ける）ときは写しを捨てて全部を頼み直す。行の配列が返ってきても（古い形）受ける。
   - `delta` を添えない頼み方（引数なし・`{ limit }` など）は、細くした行の配列のまま。画面以外の WS の使い手（試験・スクリプト）はそのまま動く。

## 理由

- 窓は受け手が「受けられる量」を表すので、受け手が自分で広げるのが筋で、取り決めの定数を変えずに済む。定数を変えると、古い相手が狭い窓のつもりで受けているところへ広い窓で送ることになり、窓超え（RESET 5・GOAWAY）で切れる。
- 大きい返事を分けて交互に流す（WS の 1 通を小分けにして、間に別の通を挟む）案は、WS のメッセージの順序の取り決め（受け手が組み立ててから渡す）を変えることになり、Node・Kotlin・Swift の組み立てと、ローカルのサーバーへの渡し方を全部直す必要がある。HTTP の別のストリームは今のフレームのまま使え、gzip とも組み合わせられる。
- 一覧の詳しい中身は、画面が使わないのに毎回送っていた。外すのが一番安い。差分にすると、2 回目からの取り直しは行数によらず小さくなる。

## 影響

- 測った数字（2,150 件・20 Mbps。届くまで / 小さい返事の待ち）は `temporary/reports/mobile-impl-transport.md` にある。窓を広げただけで往復 300 ms の一覧は 4.18 → 1.52 秒、小さい返事の待ちは 4.12 → 1.46 秒になった。
- 中継越しの画面は、一覧の最初の 1 回だけ HTTP で gzip の本文（約 110 KB）を取り、その後は WS の小さい差分になる。
- 画面とサーバーは同じホストが配るので、新しい画面と古いサーバーの組み合わせは起きない（古い画面が新しいサーバーにつながっても、`delta`・`bulk` を添えないので今までどおり配列で受ける）。
- 端末の代理（Kotlin・Swift）は `/bulk/` を他の HTTP と同じに通す。ホストの接続口の防火壁（§4.2）も GET なので通す。
