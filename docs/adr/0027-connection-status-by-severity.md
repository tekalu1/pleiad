# 0027 接続の状態を困り方で分けて出し、古いトークンでは再接続をやめる

- 状態: 承認（2026-09-27）

## 状況

接続が切れたときの表示は、脇の下の一行「接続が切れた。再接続している…」だけだった（design-system.md §2.3）。スマホ（700px 以下）では脇が閉じた引き出しの中にあり、切れても会話の画面は平常と見分けが付かず、ただの `div` なので読み上げにも届かなかった。

ブラウザーで直接開いているとき、サーバーを起動し直すと UI のトークンが変わる。古いタブは古いトークンで WebSocket を開き直し続けるが、サーバーは upgrade を 401 で断るだけで、ブラウザーからは「ただ切れた」と区別できない。画面は自動で戻ると言い続け、必要な一手（起動時に表示された URL で開き直す）を言わなかった。

## 決定

- 接続の状態は今どおり困っているときだけ出し、困り方で 2 段に分ける。
  - 自動で戻る見込みがある（切れた）: 1.5 秒続いてから、脇の下の一行に加え、脇が見えていないときは入力欄の上にも同じ一行（本文の字と弧）。送信は止めない。
  - 操作が要る（トークンが古い）: 入力欄の上に強い字の見出しと次の一手を書いた面を、脇の幅によらず出す。再接続をやめ、送信を押せなくする（欄は打てる）。
- 見分け方: WebSocket を続けて 2 回開けなかったら、HTTP で 1 回だけ確かめる。サーバーに本文を返さない `/auth-check`（認証が通れば 204、通らなければ既存の門の 401）を足し、画面は Cookie を送らずに `?token=<このページのトークン>` で聞く。401 なら古い、届かなければサーバーが止まっている（再接続を続ける）。
- WebSocket の閉じ方（未認証の接続をいったん受けて `close(4401)`）では伝えない。
- 案内の「再確認」は、押したらその場で「確認しています…」、終わったら確かめた時刻と結果（まだ開き直しが必要／サーバーに接続できない）を出す。通れば開き直し、戻った時刻を出す。
- 読み上げは画面外の `role=status` 1 か所だけにし、切れた・戻った・案内・再確認の結果を 1 回ずつ読む。
- トークンをデータフォルダーに保存して、再起動で変えないようにする案は採らない。

## 理由

- 送れない理由は、送ろうとする場所（入力欄の上）で分かるべき。脇の下は、スマホでは見えない。
- 1.5 秒待つのは、最初の開き直しで戻る瞬断（スマホの回線の切り替え）で一瞬出て消える点滅と、無駄な読み上げを避けるため。
- 自動で戻らない状態で「再接続しています…」と約束し続けるのは誤り。次の一手を書き、押しても届かない送信を残さない。
- 静的ファイルは今も未認証なら 401 を返しているので、`/auth-check` は未認証の相手に新しい情報を出さない。未認証の WebSocket をいったん受け入れるのは守りの口を緩めるので採らない。Cookie を送らないのは、別のタブが新しいトークンの Cookie を置いていても、このページの WebSocket は `?token=` で開くため。
- トークンを保存するとトークンの寿命が延び、データフォルダーを読める人が入れるようになる。起きるのはブラウザーで直接開いたときだけなので、案内で足りる。
- デスクトップ版では起きない。サーバーは本体の子プロセスで落ちたらアプリごと終わり、窓は起動のたびに新しいトークンで開く。リモートの窓はプロキシが自分のトークンを持ち、ホストの UI トークンはホスト側の接続口が付ける。
- ユーザーがモックの To-Be をレビューで承認した（文言は一般的な UI の言い回しに直す、再確認の結果をその場で分かるようにする、という指摘を反映）。

## 影響

- 画面の規則は design-system.md「接続の状態」・§2.3・§4.1、実装は `web/connection-status.mjs`（`web/client.mjs` の `connect` が使う）と `core/server.mjs` の `/auth-check`。
- リモートの窓では、中継・ホストにつながらない間の一行をバッジと同じ理由の語にする（docs/remote.md §7.2）。
