# 0167 Chrome への接続は、無停止の更新で入れ替わらない「接続の子」に持たせる

- 状態: 承認（2026-10-08。利用者の決定は「Chrome への接続を、無停止の更新で入れ替わらない側へ移す」。main も更新で入れ替わるため、置き場は保持役の子にした）。実装での違い: 設定の「切る」は接続の子に quit を送らず !close で待機に戻す（子を残し、次につないだ接続も更新を越えて持つため。core/chrome/connection.mjs の disconnect）

## 状況

[ADR 0148](0148-agent-browser-in-chrome.md) と [ADR 0153](0153-chrome-connection-waits-indefinitely-behind-os-layer.md) で、エージェントのブラウザーは PC の Chrome に CDP の ws 1 本でつなぎ、Pleiad の中継（`core/chrome/relay.mjs`）が会話ごとのポートと鍵で agent-browser に見せる形になった。Chrome は**接続 1 本ごとに**「リモート デバッグを許可しますか？」の確認を出す（0153 の状況）。

今の置き場はサーバー（core）で、接続（`core/chrome/connection.mjs`）・中継・窓の台帳（`core/chrome/windows.mjs`）がサーバーのメモリにある。OS の層（窓を隠す・前に出す。`desktop/chrome-os/win32.cjs`）は 0153 の決定 2 のとおり Electron の main にあり、窓の対応（HWND と元の拡張スタイル）は main のメモリにだけある。

無停止の更新（[ADR 0151](0151-zero-downtime-update.md)、配布版の既定）で入れ替わるものと残るものは次のとおり。

| プロセス | 更新で | 居ない時間 |
|---|---|---|
| main（Electron。`$INSTDIR`） | **毎回入れ替わる**（NSIS が置き換える） | 45〜70 秒（`docs/zero-downtime-update/design.md` §7.2 の実測） |
| サーバー（版ごとの実行場所の `pleiad-node.exe`） | 引き継ぎ（`core/handover.mjs`）で S1 → S2 に入れ替わる | 引き継ぎの間の数秒 |
| 保持役（`core/holder/`） | **入れ替わらない**（Node の組み込みだけで書いた薄いプロセス。子を Job で持つ） | — |

今のままだと、無停止の更新のたびに次のことが起きる。

- サーバーが入れ替わると ws が切れ、次に使うときに Chrome の確認がまた出る。許可を待っている途中（0153 の B）なら、出ていた確認も消える。
- 中継は起動のたびに `listenOn(0)` で新しいポートを取り（`relay.mjs` L679）、鍵も作り直す。引き継がれたターンの agent-browser の常駐は古い URL を持ったまま失敗する。
- 引き継ぎの `release` は `chromeRelay?.close()`（`core/server.mjs` L5939）を呼び、`close` → `teardown` → `scope.reset()` が**エージェントの窓を全部閉じる**。main の `will-quit` も更新の終了で `closeAgentWindows()`（`desktop/main.cjs` L457・L462）を呼ぶ。
- 配布版（パイプの経路。`mainLink`）では、サーバーが `process.parentPort` を見て OS の層を作るため（`core/server.mjs` L205）、OS の層が無い。ホストへ任せる口（design.md §7.2 の表の `remote-agent`）で直したのと同じ型の不具合で、接続そのものが使えない。

ユーザーの案は「ws を、更新で入れ替わらない Electron の main へ移す。中継と状態機械は core に残す。中継のポートと鍵は `stashOf` で引き継ぐ」だった。読むと **main も更新のたびに入れ替わる**ので、main に置くと確認はむしろ更新ごとに必ず出る（main の異常終了でも出る）。入れ替わらないのは保持役だけ。

## 決定

### 1. 接続を持つプロセス

- Chrome への ws は、**保持役の子として走る「接続の子」**（`core/chrome/link-child.mjs`）が持つ。サーバーが保持役に起こさせる（policy `'none'`）。保持役の子なので、サーバーの入れ替え（引き継ぎ・異常終了）でも、main の入れ替えでも切れない。
- 接続の子が持つのは **ws だけ**（つなぐ途中＝確認を待っている upgrade も含む）。状態機械（0153 の A〜D・出し直し）・中継・窓の台帳・映像・止める・操作待ちはサーバーに残す（0153 の決定 2 の「OS に依存させない」部分はそのまま core）。OS の層は main のまま。
- 接続の子は、走っている実行場所を使用中にする（`core/runtime-use.mjs` の `markRuntimeInUse`）。古い版の実行場所は、接続の子が終わるまで消えない。
- 札（保持役の子の label）は `{ kind: 'chrome-link', v, pipe, secret }`。新しいサーバーは保持役の welcome の子の一覧からこの札で接続の子を見つける。
- 保持役の `keepMs` は 10 分。サーバーが 10 分つながらなければ保持役が接続の子を止める（Pleiad が居なくなった後に Chrome への接続を残さない）。

### 2. 通り道

- サーバーと接続の子は、**接続の子が開く名前付きパイプ**でつながる（札の `secret` で始めの挨拶を確かめる。つなぎ手は 1 つで、新しいつなぎ手が古いほうを切る）。保持役の記録（stdout の行）と main は通さない。映像のフレームが保持役の記録の上限（1 行 16 MB・記録 32 MB）や main の入れ替えに触れない。
- 1 行 1 メッセージ。CDP のメッセージはそのまま 1 行（JSON は改行を含まない）、制御は `!` で始まる行（挨拶・`open`・`fail`・`close`・`carry`・`quit` など。形は計画）。
- **大きいメッセージは読み解かない**: 接続の子が JSON を解くのは 64 KB 未満の行だけ。それより大きい行（映像のフレーム・撮影の答え）は先頭の数百バイトで `id` を読むだけで流す。

### 3. サーバーが入れ替わるとき（引き継ぎ・異常終了）

- 新しいサーバーは、つながったときの挨拶で接続の子の状態（`idle`・`upgrading`・`open`）を受け、**そのまま取り込む**。`open` なら確認を出さずにつながった状態から、`upgrading` なら許可待ち（0153 の B）の続きから始める（出し直しの時計は接続の子が持つ upgrade を始めた時刻から数える。前に出したことのある確認は前に出さない）。
- 前のサーバーへの答えが新しいサーバーへ届かないよう、接続の子は挨拶で CDP の番号の始まり（`firstId`）を渡し、それより小さい番号の答えを捨てる。
- つなぎ手が居ない間、接続の子は `Fetch.requestPaused` を全部 `Fetch.failRequest`（`BlockedByClient`）で返す（サイトの利用の確認を、居ない間も「疑わしきは通さない」にする）。ほかのイベントは捨てる。新しいサーバーはタブ・セッションを `Target.getTargets` から組み直し、前のセッションを外して付け直す。
- 中継の状態（ポート・会話ごとの鍵・止めた印・窓の台帳と OS の層の札）は、サーバーが**接続の子に預ける**（`!carry`。変わるたびにまとめて送る）。新しいサーバーは挨拶でこれを受け、**同じポート・同じ鍵**で待ち受ける。ポートが取れなければ別のポートで立て、会話ごとの設定ファイルの `cdp` を書き直す。
  - ユーザーの案の `stashOf` には入れない。預かり物は秩序だった引き継ぎの `stash` の段でしか書かれず、5 分で古いものとして捨てられ、1 MB が上限で、サーバーの異常終了では残らない。接続の子に預ければ、ws と同じ寿命で、異常終了の後でも戻る。
- 引き継ぎの `stash` の段で、前のサーバーは中継・接続・接続の子に**手を離す**（`handOff`）。中継は agent-browser の接続を 1012 で閉じて待ち受けをやめ、窓は閉じない（`teardown` と `scope.reset` を通らない）。接続は ws を閉じずにパイプを離す。`release` は手を離した後の中継を閉じない。
- agent-browser の常駐は、同じポート・同じ鍵で中継が戻れば次の呼び出しでつなぎ直す（内蔵の中継で測った約 30 ms。design.md §7.2）。入れ替わりの数秒の間に来た呼び出しは失敗する（約 2 秒）。

### 4. main が入れ替わるとき（居ない間と、戻ったとき）

| 機能 | main が居ない間（45〜70 秒） | 戻ったとき |
|---|---|---|
| Chrome への接続・中継・映像 | 続く（接続の子とサーバーは main に頼らない） | — |
| 隠した窓 | 隠したまま（画面の外・透明度 0・素通しは窓自身の状態なので、main が居なくても崩れない）。**前面を取ったときの押し返し（0154）は効かない** | サーバーが窓ごとに預かっていた OS の札（HWND・元の拡張スタイル・Chrome のプロセス）で、新しい main に窓を取り込み直させる（`adoptAgent`）。main は窓が生きていて、Chrome のプロセスの窓で、Pleiad が付けた拡張スタイルのままのときだけ取り込む（HWND の使い回しで利用者の窓を取り違えない）。取り込んだら押し返しを再開し、置き直す |
| 新しい窓（エージェントの `createTab`・ページの `popup`） | **開かずに待つ**（main が戻るまで。20 秒で失敗を返す）。OS の層が無い間に、隠せない窓を開かない | 待っていたものを開く |
| 引き継ぐ・確認の窓を前に出す | 使えない（OS の層が要る）。画面には「Pleiad の更新中」と出す | 使える |
| 窓を閉じる | CDP の `Target.closeTarget` で閉じる | OS の層で閉じる（0154 のまま） |

- main は更新で終わるとき（`installUpdate` で `updateLeaving` を立てた後の `will-quit`・`app.exit`）、**エージェントの窓を閉じない**。更新を取りやめた（`main-leaving-cancel`）ら印を戻す。それ以外の終わり方（Pleiad の終了）では、0154 のとおり閉じる。
- サーバーの OS の層（`core/chrome/os.mjs`）は `process.parentPort` ではなく main への口（`core/main-port.mjs` の `getMainPort()`）から作る。口が切れたら待っていた呼び出しを `away` で失敗にし、つながり直したら `chrome-os-ready` を求め直す。

### 5. 引き継げないとき

次のときは今と同じく、つなぎ直して**確認が 1 回出る**。

- 接続の子の版（札の `v`）が新しいサーバーと合わない。新しいサーバーは接続の子に `quit` を送る（窓は CDP で閉じる）。
- 保持役が替わった・無くなった（保持役の異常終了、PC の再起動）。保持役の Job が接続の子も止めるので、ws は切れる。
- Chrome 自身が終わった・許可を取り消した。

### 6. Pleiad の終わりと、接続を切るとき

- Pleiad の終了・設定の「切る」・孤児の見張り（`core/orphan-guard.mjs`）による終わりでは、サーバーが接続の子に `quit` を送り、接続の子は ws（upgrade の途中なら確認も）を閉じて終わる。0153 の「接続を切る・Pleiad を終了するときは、出ている確認を閉じる」はそのまま。**更新は終了に当たらない**（確認を残し、新しいサーバーが待ちを続ける）。
- main が居ないまま窓を閉じるときは、OS の層の代わりに CDP の `Target.closeTarget` でエージェントの窓のタブを閉じる（隠した窓を残さない。0154 の「戻せなくなる窓は閉じる」を、main が居ない場合にも成り立たせる）。

### 7. 使う・使わないの切り替え

- 接続の子を使うのは、保持役を使える配布版（実行場所の置き場 `AGENT_HOST_RUNTIME_ROOT` がある・`AGENT_HOST_HANDOVER` が on）のときだけ。`AGENT_HOST_CHROME_LINK=off` で使わない（戻し道）。使わないとき・保持役につなげないときは、今と同じくサーバーの中で ws を持つ（`npm run desktop`・`AGENT_HOST_HANDOVER=off`）。
- `core/holder/*` と `core/handover.mjs` は変えない（保持役は薄いまま。引き継ぎの預かり物の形も変えない）。

### 8. 映像のフレームの費用

- 映像（0148 の右パネル、約 29 fps の JPEG、base64）は、Chrome → 接続の子 → パイプ → サーバーと、今より手元のパイプを 1 段多く通る。1100×720 で 1 枚 40〜120 KB、base64 で約 1.33 倍として、**1.6〜4.6 MB/s**【推測。第 5 段の実装で測る】。
- 費用を抑える手当て: 接続の子は大きい行を読み解かない（決定 2）、映像は右パネルで見ている間だけ流す（今のまま）、保持役の記録と main を通さない。
- 第 5 段の実機で、接続の子の CPU と、サーバーに届くまでの遅れを測る。目安を越えたら（接続の子が 1 コアの 5 % 以上、遅れが 1 フレーム以上）、映像だけをサーバーの別の ws で受ける道（映像のときだけ Chrome へ 2 本目をつなぐ。ただし 2 本目にも確認が出るので、最初の許可と同じ時に張る）を検討する。

## 理由

- **main に置かない**: main は更新のたびに入れ替わる（NSIS が `$INSTDIR` を置き換える）。main に ws を置くと、サーバーに置く今より確認が出る場面が増える（更新は毎回、main の異常終了でも）。更新で入れ替わらないのは保持役だけ。
- **保持役の中に置かない**: 保持役は Node の組み込みだけで書き、版を上げても入れ替わらない前提で薄く保っている（0151）。ws を入れると `ws` パッケージ（Chrome の 403 を見分けるのに `unexpected-response` が要る）と CDP の扱いが保持役に入り、保持役の不具合の直しが「次の PC の再起動まで届かない」ものになる。保持役の子にすれば、保持役は今の `spawn`・Job・札だけで足り、接続の子の版はサーバーの版と一緒に上がる（新しい接続の子は、次の接続から使われる）。
- **保持役の記録を通さない**: 記録は行ごとに残して ack で捨てる仕組みで、29 fps のフレームを流すと上限（記録 32 MB）に数秒で届く。サーバーが居ない間に溜める理由も無い（映像は捨ててよい）。
- **main のパイプ（MessagePort）を通さない**: main を通すと、main が居ない 45〜70 秒は映像も CDP も止まり、通り道の上で main の入れ替えに触れる。
- **保持役の外の独立したプロセスにしない**: 保持役の子なら、Pleiad が居なくなったときの後始末（`keepMs`・Job）と、新しいサーバーからの見つけ方（welcome の一覧と札）が今の仕組みでそろう。独立させると、それらを全部作り直すことになる。
- **中継の状態を接続の子に預ける**: `stashOf` は秩序だった引き継ぎでしか書かれず、5 分で捨てられ、異常終了では残らない。中継の状態に意味があるのは ws が続いている間だけなので、ws と同じプロセスに置くのが寿命として合う。
- **main が居ない間に窓を開かない**: OS の層が無いと隠せない窓（0154 の言う「画面の左上に出る窓」）が利用者の前に出る。待たせて 20 秒で失敗を返すほうが、0153 の 20 秒の待ちと同じ形で、エージェントには「待って呼び直す」で済む。
- **居ない間の `Fetch.requestPaused` を通さない**: サイトの利用の確認（0042）は、確かめられないときは止めるのが今の決まり。数秒の入れ替わりの間だけ通すと、その間のページの移動が確認を抜ける。

## 影響

- [ADR 0153](0153-chrome-connection-waits-indefinitely-behind-os-layer.md): 本文は変えない。状態の行に「接続を持つプロセスは ADR 0167（保持役の子）。OS の層は main のまま。更新は『Pleiad の終了』に当たらず、出ている確認を閉じない」と追記する。0153 の決定は Chrome への接続を core に置くとまでは書いておらず、置き場は design.md §7.2・第 7 段の計画 §1.1 の前提だった。そちらを置き換える。
- [ADR 0154](0154-agent-window-hidden-off-screen.md): 状態の行に「一部置換（0167）: 更新の終了では隠した窓を閉じない（新しい main が取り込み直す）。main が居ないときは CDP で閉じる」と追記する。
- [ADR 0151](0151-zero-downtime-update.md): 変えない。保持役の子に長く走るものが 1 つ増える（`!` の行に次いで 2 つ目）。古い実行場所は接続の子が終わるまで残る（次の Pleiad の終了か Chrome の終了まで）。
- 新しいファイル: `core/chrome/link-child.mjs`（接続の子）、`core/chrome/link.mjs`（サーバー側の口）。変えるファイル: `core/chrome/{connection,cdp,relay,windows,os}.mjs`、`desktop/chrome-os/{win32,index}.cjs`、`desktop/main.cjs`、`core/server.mjs`、第 5 段の `core/chrome/screencast.mjs`・第 6 段の `core/chrome/control.mjs`（新しい cdp への付け直しと、止めた印の預け）。量は計画（`temporary/reports/chrome-connection-in-main-plan.md`）。
- 試験: 偽の Chrome（`tests/lib/fake-chrome.mjs`・`fake-chrome-browser.mjs`）と保持役（`tests/lib/holder-harness.mjs`）で、接続の子を挟んだサーバーの入れ替え（引き継ぎ・異常終了・版の不一致）を確かめる。偽の main（`tests/lib/fake-chrome-os.mjs`・`desktop/server-link.cjs`）で、main が居ない間の窓の扱いと取り込み直しを確かめる。実機の受け入れは第 7 段の §10.2 の ⑧（無停止の更新の後）に、「確認が出ない」「許可待ちの途中の更新で確認が残り、許可すると続く」「隠した窓が更新の後も見えない」を足す。
- 文書: `docs/zero-downtime-update/design.md` §7.2 の表にエージェントのブラウザー（Chrome）の行を足し、最後の段落（「どこに置くかはその段で決める」）をこの ADR への参照にする。`docs/inapp-browser.md` の Chrome の章に接続の子を書く。`AGENTS.md` の環境変数の表に `AGENT_HOST_CHROME_LINK` を足す。
- 残る危険（受け入れる）:
  - main が居ない最大 70 秒、隠した窓が前面を取っても押し返さない（ページの `window.open` など。エージェントの `Page.bringToFront` は中継が握りつぶす）。
  - 保持役が替わる・接続の子の版が合わないときは、確認が 1 回出る。
  - 古い版の実行場所が、接続の子が終わるまで残る（容量。1 版分）。
  - 入れ替わりの数秒、agent-browser の呼び出しが失敗する。
  - 保持役ごと落ちたとき（PC の再起動を除く）は、窓の OS の札も失われ、隠した窓が残る。今の main の異常終了と同じで、この ADR では直さない。
