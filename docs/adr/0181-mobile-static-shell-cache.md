# 0181 モバイル版は画面の殻（web/ の静的ファイル）を端末に持ち、版が変わったときだけ取り直す

- 状態: 提案（2026-10-09。方針「画面の殻は端末に持ち、版が変わったときだけ取り直す」は利用者が承認。方式はこの ADR で選ぶ）
- 日付: 2026-10-09
- 番号: 0181 は仮。main に入れるときに次の番号へ振り直す
- 関連: docs/remote.md §8.6（今の振る舞い）、§4.2（防火壁）、§8.3（端末内プロキシ）、docs/zero-downtime-update/design.md §8（`pleiad-build` で画面を 1 回だけ読み直す）

## 状況

モバイル版の殻（Capacitor）は、ホストの `web/` を端末内プロキシ（`127.0.0.1:<p>`）と中継を通して開く。起動のたびに静的ファイル 243 本（4.4 MB）を 1 本ずつ中継の往復で取り、キャッシュも効かない。RTT 300 ms・CPU 4× で、画面が ready になるまで 15.6 s、会話が描けるまで 35.5 s かかっていた（temporary/reports/mobile-perf.md）。遅さの最大の原因はこの往復の数。

条件:

- 版が変わったら必ず取り直す。古い殻を出し続けない。
- 古いアプリ × 新しいホスト、新しいアプリ × 古いホストのどちらも動く（遅いのは構わない）。
- デスクトップ版・ブラウザーの直のつなぎを壊さない。開発の流れ（`web/` を要求のたびにディスクから読む）を残す。
- トークン付きの URL と認証の扱いを弱めない（§4.2）。

## 検討した方式

| 方式 | 内容 | 採らない／採る理由 |
|---|---|---|
| (a) Service Worker | `web/` に SW を置き、殻をオリジンの Cache Storage に入れる | **採らない。** 端末内プロキシのオリジンは `127.0.0.1:<p>` で、ポートを移ると（iOS の前面復帰・ポートの衝突）保存が丸ごと別物になる。WKWebView の SW は App-Bound Domains の制約があり、`127.0.0.1` の平文のオリジンで確実に動く保証が無い。`web/` に SW の更新の流れ（skipWaiting・版の食い違い）が増え、デスクトップ版・ブラウザーにも効いてしまう |
| (b) 端末のネイティブ側で持つ | プロキシ（Node・Kotlin・Swift）が殻をファイルに保存し、自分で返す | **採る。** オリジン・ポートに縛られない（ホストごとのファイル）。`web/` は変えない。プロキシはもともと認証と `Host` の照合をしているので、その後ろで返せば守りは同じ |
| (c) 版を 1 往復で確かめ、束ねて取る | ホストが `web/` の中身のハッシュを key にした 1 本の束を配り、端末は `have=<key>` で尋ねる（同じなら 304） | **採る（(b) と組み合わせる）。** 243 往復が「確かめの 1 往復」になり、変わったときも 1 本（gzip で約 1.4 MB）で済む。key は中身のハッシュなので、版の番号を上げ忘れても、開発中にファイルを書き換えても必ず取り直す |
| (d) HTTP キャッシュ（`Cache-Control`・ETag） | 静的ファイルに検証子を付け、WebView のキャッシュに任せる | **採らない。** WebView の HTTP キャッシュはオリジンごとでポートが変わると失われる。ETag でも 1 本ごとの再検証の往復は残り（243 回）、`max-age` で往復を消すと版が変わったときに古い殻が出る。消すには import の URL に版を埋め込む書き換え（`web/` 全体）が要る |

## 決定

1. **ホストに `GET /static-bundle?have=<key>` を足す**（`core/static-bundle.mjs`）。ホストのトークンの確かめの後ろに置く（無ければ 401。§4.2 の防火壁はそのまま通す）。中身は静的ファイルの口が配るもののうち拡張子が MIME にあるもの全部と `/vendor/i18next.mjs`。`index.html` は配るときと同じ `pleiad-build` の置き換えを済ませて入れる。`have` が今の key なら 304、違えば 200 で束を返す。要求のたびに `web/` の大きさと更新時刻を見て、変わっていれば作り直す（開発の流れでも次の読み込みで新しい key になる）。ふつうの静的ファイルの応答は変えない。
2. **束の形**（`core/remote/static-bundle.mjs`）: `"PLSB"` | u32（BE）の見出しの長さ | 見出しの JSON `{ format: 1, key, files: [{ path, type, size }] }` | 本文を files の順に。key は files の順に `"<path>\n<type>\n<size>\n"` と本文をつないだ SHA-256 の hex。読む側は magic・見出し・パスの形（`..` 無し）・type の改行・大きさ・余りのバイト・key を全部確かめ、合わなければ使わない。上限は展開の前後とも 64 MiB。
3. **端末は殻をホストごとに 1 つのファイルで持つ**（`<端末の保存場所>/static/<hostId>.bin`。圧縮しない形で、置き換えは原子的に）。ホストを忘れたら（remove）消す。Node（デスクトップ版の端末）・Kotlin・Swift の 3 つのプロキシが同じ形で持つ。
4. **ページの読み込みのたびに確かめる。** プロキシは `/` か `/index.html` の要求が来るたび、チャネルが ready になった後でホストに尋ねる（1 往復）。304 なら持っている束、200 なら新しい束を保存して使う。ほかの静的ファイルの要求は、直近の確かめの答えを待って使う。オフラインの扱い（案内のページ）は今と同じ。
5. **束から返すのは「クエリが `token` だけの GET/HEAD」で、束にあるパスだけ。** トークン・`Host`・メソッドの照合はこれまでどおりプロキシが先に行う。束から返すときに付ける Cookie はプロキシ自身のもの（`token` のクエリが正しいときだけ）。ホストのトークンは端末に出ない。束に無いもの・束が使えないとき（古いホストの 404・失敗・壊れたファイル）は、今までどおり 1 本ずつホストへ流す。
6. **古いアプリ・古いホスト**: 古いアプリは `/static-bundle` を呼ばないので今までどおり。古いホストは 404 を返し、新しいアプリは今までどおり流す。どちらも遅いだけで動く。
7. **転送の圧縮は `/bulk/<id>`（ADR 0179）と同じ HTTP の gzip にそろえる。** 要求の `accept-encoding` に gzip があればホストは gzip（水準 6）で返して `content-encoding: gzip`・`vary: accept-encoding` を付け、無ければ縮めない。束だけの圧縮の取り決め（独自のクエリや見出し）は作らない。Node・Kotlin は `accept-encoding: gzip` で取る。Swift は Apple の Compression があるときだけ付け、gzip の頭と尾（ISIZE）を読んで中の deflate を戻す（Windows・Linux の試験では付けず、縮めない束を受ける）。CRC は見ず、束の key（全ファイルの SHA-256）で確かめる。

## 理由

- 往復の数が遅さの本体なので、往復を 1 にする (c) が最も効く。中身のハッシュを key にすれば「版が変わったら必ず取り直す」が仕組みで保たれ、ホストの版の番号や再起動に頼らない。
- 保存をオリジンの外（ネイティブのファイル）に置けば、ポートが変わっても、WebView の保存が消されても効く。(a)・(d) はどちらもオリジンに縛られる。
- 返すのはプロキシの認証の後ろなので、守りの境界は今と同じ。束の口もホストのトークンの後ろで、中継から届く要求は §4.2 の接続口がトークンを差し込んだものだけ。
- `web/` を変えないので、デスクトップ版・ブラウザーの直のつなぎと開発の流れには影響しない。

## 影響

- 端末の保存が 1 ホストにつき約 5 MB 増える。
- ページの読み込みのたびに 1 往復の確かめが入る（今までの 243 往復の代わり）。版が変わった最初の読み込みは束 1 本（約 1.4 MB）を取る。
- ホストの `web/` が束の上限（64 MiB）を超えると 500 になり、端末は 1 本ずつ流す形に戻る。
- 束の形を変えるときは `format` を上げる。読む側は知らない `format` を使わない（今までどおり流す）。
