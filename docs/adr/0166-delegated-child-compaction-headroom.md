# 0166 委譲の子の自動圧縮の閾値は、固定の部分 + 空きにする

- 状態: 承認（2026-10-08）
- 関連: [0163](0163-delegated-child-compaction-threshold.md)（委譲の子の自動圧縮。閾値の決め方をこの ADR で置き換える）、[0051](0051-auto-compaction-min-150k.md)

## 状況

[ADR 0163](0163-delegated-child-compaction-threshold.md) は、委譲の子の Claude の自動圧縮の閾値を固定の値（`delegatedTokens`。既定 15 万）にした。ところが子の文脈には、作業を始める前から入っている「固定の部分」（システムプロンプト・道具の定義・Pleiad の指示・CLAUDE.md・Skill の一覧など）があり、圧縮しても減らない。実測（2026-10-08）では固定の部分は 7.1 万〜7.2 万で、圧縮した直後の文脈は 8〜9 万になる。

固定の部分は作業場所（CLAUDE.md・Skill）・モデル・MCP の数で変わる。閾値が固定だと、固定の部分が大きい作業場所では作業に使える空きが小さくなり、圧縮してもすぐ次の圧縮が来る。利用者は閾値を 18 万に上げて回避していたが、作業場所ごとに合う値が違う。

## 決定

**委譲の子の閾値 = 固定の部分 + 空き（`delegatedHeadroom`。既定 10 万）。** 窓（`CLAUDE_CODE_AUTO_COMPACT_WINDOW`）は閾値 + 33000 で、ADR 0163 と同じく 10 万〜100 万に丸め、閾値は 7 万を下回らない。

- **固定の部分の測り方:** Claude の会話の最初のリクエストの文脈。新しい会話の最初の返答（サブエージェントの返答を除く）の `message.usage` の `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`。Claude の接続部が `contextBase` の出来事として 1 度だけ出し、サーバーが子の会話（`store` の `contextBase`）と直近の値の台帳に残す。
- **子の最初のターン:** まだ自分の値が無いので、直近の委譲の子の値から見積もる。同じ作業場所・同じモデル（頼んだモデルの名前）の直近 → 何でもよいので直近 → 無ければ定数 7 万。2 ターン目からは子自身の値を使う。
- **直近の値の台帳:** データ置き場の `context-bases.json`（作業場所 × モデルで 50 件まで。古いものから捨てる）。再起動をまたいで残る。
- **設定:** 自動圧縮の設定（`settings.set compaction.auto`）の `delegatedTokens` をやめ、`delegatedHeadroom` にする。既定 100000、0 はオフ（Claude Code の既定に戻す）、0 以外は 30000〜1000000。30000 は、圧縮した直後の文脈が固定の部分より 1〜2 万多いので、それより小さいと圧縮の直後にまた圧縮するため。
  - 移行はしない。prefs に `delegatedTokens` が残っていても読むときは無視し（読み込み・保存は失敗しない）、空きは既定の 10 万になる。次に保存するときに消える。
- **確かめられるようにする:** 子のターンごとに使った閾値と内訳（`{ threshold, base, source, headroom }`。source は own・same・recent・default）を委譲タスクの記録の `compaction` に残す。委譲のカードの詳細と、上に留めた子の詳細に「圧縮の閾値: 171k（固定 71k + 空き 100k） · この子の値」の形で出す。
- 付ける相手（委譲の子の Claude のターンだけ）・利用者の `process.env` を優先すること・放置圧縮とは独立に効くことは ADR 0163 のまま。

## 理由

作業に使える空きを一定にすると、作業場所やモデルによらず「圧縮から次の圧縮まで」の長さがそろう。固定の部分は最初のリクエストで正確に分かり、同じ子の中ではほとんど変わらないので、2 ターン目からは子自身の値で足りる。最初のターンだけは測る前に窓を決める必要があるため、同じ作業場所・同じモデルの直近の値で見積もる（同じ作業場所なら CLAUDE.md・Skill が同じで、値がほぼ一致する）。

測るのに Claude Code の `getContextUsage()` のような別の問い合わせは使わず、すでに流れている `usage` を読むので、リクエストが増えない。

## 影響

- 既定の閾値は 15 万から「固定の部分 + 10 万」（実測の作業場所で 17.1 万）に上がる。前の版で 18 万にしていた利用者は、既定（10 万の空き）に戻る。
- 子の最初のターンの見積もりは、依頼の文（task・context）も固定の部分に含めて測った他の子の値を使う。依頼の文が長い子どうしでは数千〜数万の差が出うる。2 ターン目からは子自身の値なので、差は最初のターンだけ。
- 同じ作業場所・同じモデルの判定は頼んだモデルの名前（空なら既定）で行う。既定のモデルが変わると、同じ名前（空）で別のモデルの値を使うことがある。
- 委譲のカードに出る閾値は、子の直近のターンで使ったもの。設定を変えても、子が次のターンを始めるまでカードは前の値のまま。
- データ置き場に `context-bases.json` が増える（`tests/data-writes-allowlist.mjs`）。
