# 0080 セッション検索を会話の本文まで広げる（本文の写しをメモリに持ち、都度走査する）

- 状態: 承認（2026-10-03）

## 状況

脇の検索（`web/side.mjs` の `matchesQuery`）は、題・状態・作業ディレクトリの絶対パスを 1 つの文字列にして、打った文字列全体を部分一致で探すだけだった。会話の本文は見ず、空白で区切った複数語は 0 件になり、全角半角は別物で、`dev` のような語がパスの途中に当たって全部の会話が当たる。委譲の子の会話（実データで 927 件のうち 457 件）は一覧に出ないので探せない。

「あの話をした会話」を探す用途には本文が要る。実データ（2026-10-03）の量と速さは次のとおり。

- 本文（人と AI の発言）は 813 万字。会話 812 件・最大 23.5 万字。ツールの出力は 2.3 億字で全体の約 6 割を占め、雑音も多い。ツールの入力のうち command・path・pattern・url の短い項目は 400 字で切って 1,210 万字。
- 812 ファイルを読んで JSON を解くのに 1.6〜1.7 秒（1 回だけ）。全件を走査して AND と一致の数え上げまで 3.6〜6.6ms（ツールの入力を足しても 8〜22ms）。メモリは畳んだ本文だけで +60MB、元の文字も持って +87MB、ツールの入力まで足して +96MB。

## 決定

1. 索引は作らない。会話ごとの発言の写し（`{ uuid, role, at, text, 畳んだ text }`）をメモリに持ち、探すたびに全件を走査する（`core/session-search.mjs`）。
   - 写しの元は、Pleiad が持つ会話の `conversations/<id>.json` を直接読んだもの（記録に載せず、本文が二重にメモリへ載らない）と、それ以外の会話のバックエンドの `getMessages`。起動の少し後から、新しい会話を先に、並列 2 本で裏で読む。
   - 更新: ターンの終わりに読み直す。`loadSession` が読んだ履歴はそのまま写しに入れる（読み込みの追加は無い）。一覧の `lastModified` が写しより新しい会話は、探すときに読み直し、短く待って間に合わなければ古い写しで答える。
   - 起動直後など、探された範囲の写しが揃っていない間は、読めた分で答えて `partial: true` を返す。
2. 対象は人と AI の本文だけ。thinking・ツールの出力・圧縮の要約・システムの行（`kind` 付き）・委譲の完了通知・提示（Visualize）は写さない。ツールの入力は短い項目だけを別に持ち、`includeToolInputs` のときだけ当てる（既定は対象外）。
3. 照合: 空白（全角を含む）で区切った語は AND で、語ごとに題・状態・場所・どの発言に当たってもよい。`"…"` で囲んだ語は畳まず（大小・全角半角を区別して）そのまま、ほかは NFKC と小文字に畳んだ部分一致。場所は作業ディレクトリのフォルダー名だけに当てる（パスで絞るのは `filters.cwd`）。演算子（`from:` など）は解かない。
4. 結果は会話の平らな一覧（状態ごとの木にしない）。委譲の子は既定で含めず、`includeDelegated` で含める。アーカイブは扱わない（Pleiad にその考えが無い）。関連度は「題に当たった語 ×4・全部の語が 1 つの発言に揃えば +2・`log2(1 + 一致した発言の数)`・新しさ（30 日で 1 減る）」で、同点は新しい順。抜粋に選ぶ発言は、題に無い語を多く含む発言 → 語を多く含む発言 → 新しい発言。
5. 入出力は 1 つの関数 `search(input) → SearchResult`（と `status() → { indexed, pending, updatedAt }`）。画面・MCP・CLI は `core/ops/` の操作 `sessions.search` から同じものを呼ぶ。この段では WebSocket のコマンド・MCP・CLI・画面は足さない。

## 理由

- 走査は 5ms 前後で、打つたびに探しても入力の待ち（120ms）に収まる。会話が 10 倍になっても 50〜70ms の見込み。重いのは最初の読み込みとメモリだけで、どちらも裏で済ませ、`partial` で正直に伝えれば足りる。
- 日本語は語の区切りが無いので、転置索引は n-gram（本文の数倍のメモリ）になる。走査が 5ms で済む今は利点が無い。SQLite FTS5（trigram）は `node:sqlite` の版依存と、3 文字未満の語（「翻訳」「CI」）を引けない弱点があり、スキーマ・移行・作り直しの手間もかかる。毎回ファイルを読む方式は 1 回 1.7 秒（ネイティブ側を含めればそれ以上）で採れない。
- 部分一致・NFKC・`"…"` の厳密一致が、そのまま `includes` で書ける。結果は常に最新で、索引の更新漏れという故障の形が無い。
- ツールの入力は「あのコマンドを打った会話」の用途があるが、当たりが倍になる（`worktree remove` が 105 → 222 件）ので、既定は外して選ばせる。出力は雑音が大きく対象にしない。
- 場所を絶対パスの全体に当てると、`dev` や `temporary` が全部の会話に当たる。

## 影響

- ホストのメモリが、実データの規模で 60〜100MB 増える（会話が増えれば比例する）。起動の後、数秒〜十数秒の間は `partial` になりうる。
- Pleiad が持つ会話で、CLI 側だけで進んだ末尾は、その会話を開く・ターンが終わる・一覧の `lastModified` が進むまで写しに入らない（保存分を先に読むため）。
- 次の段で、写しの軽い版（本文だけ。推定 20〜30MB）を `<data>/search-text/` に書いて起動時の読み込みを省くことと、会話が 5,000 件を超えたときの SQLite FTS5 を検討する。
- 仕様の今の形は `docs/design.md`「セッション検索」。
