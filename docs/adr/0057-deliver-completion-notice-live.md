# 0057 委譲の完了通知を、完了した時点で依頼元へ届ける

- 状態: 提案

## 状況

委譲した Pleiad タスクの完了通知は、依頼元の会話が走っている・裏の作業が残っている・人の送信待ちがある間は `pending` のまま保留され、依頼元が空いてから新しいターンとして 1 件ずつ送られていた（[ADR 0044](0044-task-instruction-delivery.md) の配送の規則を通知にも使う）。

依頼元が 1 つの長いターンで作業を続けると、通知は完了から遅れて届いた（2026-09 の実例では、完了からおよそ 1 時間後）。依頼元は `ply_task_wait` や報告ファイルで結果を先に受け取って作業を進めており、読み終えた結果の通知が、ターンの後に完了の数だけ別々のターンとして届いた。依頼元が通知を待てず、自分で報告ファイルを監視するようになり、その監視が終わらずに残る原因にもなった（issue tekalu1/pleiad#35）。

Claude・Codex・fake は、走っているターンへ入力を足す `control.steer(item)` を公開している（人の「作業中のメッセージ送信」。`docs/design.md`）。Antigravity は持たない。

## 決定

1. **走っているターンへ届ける。** 完了通知が `pending` になり、依頼元の会話がターンを実行中で、`control.steer` があり、次ターンの設定の予約が無く、人の送信待ち（outbox の未送・失敗・保留・結果不明）が無いとき、通知本文を `steer` で今のターンへ渡す。人の送信を優先する決まりは変えない。圧縮のターン・中断や終了に向かっているターン・途中送信を持たないバックエンドには渡さない。裏の作業（`awaitedBackground`）が残っているだけでターン自体は走っていないときは、今までどおり保留する。
   - 通知は人間の発言ではない。outbox を通さず、本文のハッシュを `taskNotices` に記録し（履歴が通知として描く）、画面へは今の完了通知と同じ 1 行（`taskNotice`）を出す。人間の吹き出しや送信中の表示にはしない。
   - 状態は、送る直前に `delivering` を保存し（保存できなければ送らない）、受理（true）なら `sent`、受理できない（false）なら `pending` に戻して今の「空いたら新しいターン」の経路へ、結果不明（throw）なら `unknown`（自動で再送しない）。
   - 「渡った」合図を後から出すバックエンド（`steerConfirms`。Claude・Codex）では、合図（`userMessage.delivered`）で通知の 1 行を出す。読まれないままターンが死んだ（`userMessage.dropped`、または合図が来ないままターンが終わった）ときは `sent` を `pending` に戻し、空いたときの経路で送り直す。人間の発言と違い、通知は送り直してよい（内容は結果の写しで、二重に届いても害が小さい）。
2. **受け取り済みの通知は送らない。** 依頼元が `ply_task_status` / `ply_task_wait` で終了状態（`completed` / `failed`）と結果を受け取ったら、通知を新しい状態 `read` にして後から送らない。結果が長く `nextOffset` が残っていても、受け取った時点で配達済みとする。`ply_task_list` は結果を返さないので対象にしない。実行中の `status` も対象にしない。終わった直後で通知がまだ `pending` になる前（`none`）に受け取ったときも `read` にし、直後の `run.notice` が `pending` に戻さない。`ply_task_send` は `none` に戻す（次に走る回の結果は通知する）。`read` は前の回の拒否コマンドを渡した印としても `sent` と同じに扱う。
3. **まとめる。** 空いたときの経路でも途中送信の経路でも、同じ依頼元へ届ける `pending` が複数あれば 1 つの通知（1 ターン、または 1 回の途中送信）にまとめる。本文は各 taskId の節（`--- <taskId> ---`）を完了の早い順に並べ、見出しの文言は辞書（`agent:delegation.noticeBatch` / `noticeSection`）に置く。1 件のときは今までの文のまま。結果は 1 件 16000 字までで、まとめたときは全体で 16000 字ほどに分け、切った分は `ply_task_status` の `offset` で読める。同じ依頼元への配送は同時に 1 つだけにし、その間に完了した分は次の配送でまとめる。
4. 無音通知・長いコマンドの通知（[ADR 0048](0048-delegation-silence-notice.md)）は変えない。これらは走っているターンへ途中送信せず、今までどおり依頼元が新しいターンを受けられるときだけ送る。

## 理由

通知の目的は、依頼元が結果を知って続きの作業を進めること。完了した時点で届けば、依頼元は報告ファイルの監視や `ply_task_wait` の空回しを要らなくなる。

走っているターンへの入力は、人間の「作業中のメッセージ送信」が既に持つ経路なので、新しい配送の仕組みを作らない。受理・不明・拒否の 3 値と「渡った」合図は、人間の発言と同じ意味で使える。通知は人間の発言と違って中身が結果の写しなので、渡らなかったときの送り直しを許す。

結果を先に読んだ通知は、内容が古く（読み終えた結果と同じ）、依頼元のターンを 1 つ消費するだけになる。まとめれば、複数の子が続けて終わったときのターン数も抑えられる。

## 影響

- 通知の状態に `read` が加わる（`none` → `pending` → `delivering` → `sent` / `unknown`、`suppressed`、`read`）。読み手は `core/agent-tasks.mjs`・`core/completion-notices.mjs`・`core/server.mjs` に限られ、画面は `unknown` だけを見る。`read` は `NOTICED` に含める。
- `createAgentTasks` の `deliver` は 1 件のタスクではなく、同じ依頼元のタスクの配列を受け取る。`steerable`（走っているターンへ今すぐ渡せるか）を新しく受け取る。`ready`（新しいターンを受けられるか）は無音・コマンドの通知と共通のまま。
- 走っているターンへ渡した通知は、画面の 1 行では「タスクの結果で再開」と同じ見せ方になる（ターンは再開していないので、文言はやや実際とずれる）。
- バックエンドの実機での注意点は `temporary/reports/delegation-notify-live.md` にまとめた（Claude の入力が閉じる終わり際、Codex の `turn/steer` の `expectedTurnId`）。実 LLM での確認は未実施。
- `docs/agent-delegation.md`「完了通知」を今の形に書き直した。
