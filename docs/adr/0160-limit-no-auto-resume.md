# 0160 上限で止まった会話を自動で再開しない

- 状態: 提案（廃止そのものは利用者の決定。2026-10-08）
- 置き換えた: [0132](0132-limit-resume-auto-only.md)（全体）

## 状況

[ADR 0132](0132-limit-resume-auto-only.md) は、使用量の上限で止まった会話を解除時刻に自動で再開するようにした。`schedule.json` の予定（`kind: resume`）が解除時刻に再開し、解除時刻が分からない上限は 30 分ごとに使用量を確かめて試しに再開し（間隔は 6 時間まで伸ばす）、起動時とスリープ解除時は過ぎた会話を一斉に再開して予定を置き直した。会話ごとに［再開しない］／［自動で再開する］を切り替えられ、自動で戻れなかったときは自動再開を外して失敗として通知した。

使ってみると、次の問題があった。

- 止まってから時間がたつと前提が古くなる（main やほかの作業が進む）のに、人が見ないまま動き出す。実例（2026-10-07〜08）: 依頼元が作業を別の委譲の子へ移した後、古い委譲の子が利用枠の解除で自動再開し、同じ worktree に重ねて書き込んだ。
- 委譲の子が上限で止まると、依頼元が気付いて別のバックエンド・アカウントへ振り直す。自動再開は二重作業にしかならない。
- 解除の直後の新しい枠を、止まっていた会話が一斉に使う。
- 得られるのは「人が戻って再開を押すより数時間早く続く」ことだけで、上限中に送った指示が解除時刻に流れる動きで代わりになる。

## 決定

**上限で止まった会話は、自動では再開しない。** 続けるのは、人の「再開」と、人が送った指示だけにする。

- 消すもの: 解除時刻の再開の予定（`schedule.json` の `kind: resume` を置く・撃つ処理）、解除時刻が分からない上限の使用量の見回り・試しの再開・間隔の伸ばし、起動時とスリープ解除時の一斉の再開と予定の置き直し、会話ごとの［再開しない］／［自動で再開する］（会話末尾のリンクと操作 `sessions.setAutoResume`、出来事 `limitResumeChanged`、会話の印 `interrupted.autoResume`・`autoResumeOff`）、自動で戻れなかったときの失敗の通知、画面の「解除時刻を過ぎて 2 分たっても自動再開の印が残る会話は普通の再開にする」扱い、自動で戻る会話の時計の印（入力欄の「◷ 2:30 に再開」「◷ 解除を確認中」、脇の行の「◷ 2:30 に再開」）、終了の確認の「上限の解除後の再開が N 件」（`running` の `scheduled.resume`）。
- 残すもの: 上限の検出と保存（`interrupted: { at, reason: "limit", resetsAt, window, account, backend, model }`）、会話の末尾の行と普通の「▶ 再開」、解除前の入力欄の押せない時計「◷ 2:30 に解除」と、解除前の人の再開を断ること（`LIMIT_WAITING`）、送信予定（`kind: send`。[ADR 0103](0103-scheduled-send.md)）、入力欄のアカウントの札で替えて送る逃げ道（替えると止まった枠の待ちが解け、送った指示がすぐ流れる）。
- **上限中に送った指示**は、人が明示した続け方として残す: 送信待ちに置き、解除時刻に人の操作なしで流す（会話ごとのタイマー。起動時とスリープ解除時に置き直す。閉じている間に過ぎていれば、置き直した時点で流す）。
- **解除時刻が分からない上限は待たせない**: 送った指示はすぐ送る（まだ上限なら、また上限で止まるだけ）。人の「再開」も断らない。0132 で自動再開を外した会話と同じ扱い。
- 保存する解除時刻は未来のときだけ。もう過ぎている（取得元が古い）なら `null`（分からない上限として扱う）。
- 上限で止まったことは、今までどおり完了として通知しない（脇の行の中断の三角で見せる）。
- 前の版が残したデータは読まない: `schedule.json` の `kind: resume` の行は起動で戻さず、撃たない（次に予定を保存したときにファイルから消える）。会話の `interrupted.autoResume` と `autoResumeOff` は読まない（DB の形は変えない。残った値は害がない）。自動再開の印が付いていた会話も、普通の上限の会話として人の「再開」で続く。

## 理由

自動で動き出すのは、止まった時点の前提がまだ正しいときだけ役に立つ。上限は数時間〜数日続くので、その間に人や依頼元が作業を動かしていることが多く、自動の再開は古い前提での二重作業になる。続けたい人は、戻ってきて「再開」を押すか、上限中に指示を送っておけば解除時刻に流れる。後者は人が中身を決めて送ったものなので、時刻に流しても前提のずれが起きにくい。

解除時刻が分からない上限で指示を待たせると、流す時刻が無い（0132 は使用量の見回りで流していた）。待たせたまま人の「再開」を待つと、送ったのに何も起きない。すぐ送れば、解けていれば続き、解けていなければまた上限で止まって人に見える。

## 影響

- ADR 0132 を全体として置き換える。ADR 0093 のうち 0132 でも有効だった決定（上限の検出と保存・上限中の指示の送信待ち・再開で送るもの・アカウントの自動切り替えをしない）はそのまま有効。ADR 0103 は変わらない（日時の候補に「上限の解除後」は無いまま）。
- 操作 `sessions.setAutoResume` を消す（ops の snapshot も）。WS の出来事 `limitResumeChanged` と `running` の `scheduled.resume` を消す。辞書から自動再開の文言を消す。
- 会話の末尾の 2 行目は「2:30 に解除。解除の後に「再開」で続けられます」（解除時刻が分からなければ「解除時刻は分かりません。「再開」で続けられます」）になり、リンクは無くなる。
- 既知の制限（0132 から続く）: 再起動をまたぐと送信待ちは保留（`paused`）に戻るので、解除の前に送った指示は、再起動の後は人の「再開」で送る。
- 通知の種類は変わらない（自動で戻れなかったときの失敗は完了通知の `error` を使っていた）。Android（`mobile/`）に上限の自動再開に依る種類・文言は無い。
- 画面は `docs/design-system.md`「中断と再開」、動きは `docs/design.md`「中断と再開」を今の形に直した。
