互換の接続先を、エージェントごとに登録して会話で選ぶ

2026-09-23 に案 A で実装済み。モックとの差分と設計は docs/design.md「互換の接続先」を参照（案 B は採らなかった）。
procway-code の代わりに、Claude Code と Codex で互換 URL（OpenRouter・自前の LiteLLM・ローカルの Ollama など）を使えるようにする案です。
操作できるモックです。通信・保存はしません。再読み込みで初めに戻ります。

モックの操作
モデルのチップ（右下の「▾」）を押すと面が開きます。

決めたこと

  • チップは 3 つのまま。モデルのチップの面で「エージェント」の下に「接続先」の節を置く。先頭は「公式」（既定の札）、下に登録した互換の接続先。
  • 互換の接続先を選ぶと、モデルの節はモデル ID の入力欄＋その接続先の一覧に替わる。空ならメインに割り当てたモデル（「既定」の札）。
  • チップの字は「OpenRouter · glm-4.6」。モデル ID の / より前は省き、全体は title に出す。
  • Claude の互換の接続先では段（エフォート）を送らない。無効にして理由を書く。Codex の互換の接続先は既定の段が分からないので「既定」の段を作らない（design-system の規則どおり）。
  • Claude のアカウントの節は残し、互換の接続先では選べない見た目にして一文で理由を示す（節ごと消すと、公式に戻したときにどれが効くのか分からなくなるため）。
  • 変更は「次のターンから適用」に出して取り消せる。分岐・委譲・新しい会話への引き継ぎは他の設定と同じく接続先も継ぐ。委譲先のエージェントが違うとき（Claude の会話から Codex へ委譲など）は形式が合わないので公式に戻す。

決めたこと

  • 各エージェントの行に「接続先」を置き、押すと同じページの下に管理の面が開く（procway・Claude のアカウントと同じ部品と開き方）。
  • 一覧の先頭は「公式（ログイン中のアカウント）」。消せない・編集しない行で、アカウントの切り替えは「アカウント」の側。
  • 互換の行には、形式・URL・認証・キーの保存場所、最後の確認の結果、モデルの割り当て、「この接続先で使えないもの」を出す。
  • 確認に失敗している接続先は ⚠ と強い字（警告色は使わない）。消すと、その接続先を選んでいる会話は次のターンの前に選び直しを求める（黙って公式に戻さない。アカウントと同じ扱い）。
  • 「既定にする」で新しい会話の既定にできる。

モックの操作

決めたこと

  • 流れは ① 種類（プリセット）→ ② 接続情報 → ③ 接続を確認 → ④ モデル → ⑤ 保存。確認が通るまで保存は出ない（procway と同じ二段）。URL・キー・認証を変えたら確認し直し。
  • 確認は本物の 1 リクエスト。Claude Code は POST /v1/messages（max_tokens 1）を Bearer と x-api-key で試して認証方式を決め、Codex は POST /responses を打つ。モデル一覧は GET /models で取る（取れなくても失敗にしない）。
  • Codex では Chat Completions だけの先（DeepSeek・Kimi・Together AI など）はプリセットに出さず、注記で LiteLLM での変換を案内する。カスタムで入れた場合は確認で理由つきで失敗させる。
  • Claude Code は役割の割り当て（メイン / Opus 相当 / Sonnet 相当 / Haiku 相当）。Haiku 相当は背景の処理とタイトル生成に使う。Codex は既定のモデルとコンテキスト長。
  • キーは伏せ字で受け、OS の資格情報に保存して以後は表示しない。キー不要のローカル（Ollama など）は空で通す。
  • 主要操作（塗り）は「接続を確認」か「保存」のどちらか 1 つだけ。

決めたこと

  • 互換の接続先で無くなるもの: 使用量（サブスクの枠）・Web 検索・Fast mode・料金の目安。ほかにリモートの操作、MCP のツール検索（既定で切れる）もあるが、Pleiad の画面に出ていないものは並べない。
  • 出す場所は 3 つ: ① 接続先の一覧の各行（画面 2）、② モデルのチップの面の接続先の節の下（画面 1。選んでいる間だけ）、③ 設定 › 使用量（接続先ごとの見出しの下に「この接続先の使用量は表示できません」）。
  • Pleiad には会話の中に使用量の表示が無いので、「会話中の使用量」は ② と ③ で代える（方針から外れた点。報告に記載）。
  • 使用実績（tokens）は Pleiad が数えられるので残す。参考費用は「不明」。
  • Web 検索が失敗したツールのカードには、Pleiad が理由の一文を足す（エージェントの失敗文だけでは接続先が原因だと分からないため）。

案 A: 接続先の節案 B: エージェントに並べる
わかりやすさ「誰が（エージェント）」と「どこにつなぐか（接続先）」が分かれる。節が 1 つ増える。選ぶのは 1 回だけ。ただし「Claude Code — OpenRouter」が別のエージェントに見え、切り替えると会話を引き継ぎ直すように感じる。
一覧の長さエージェントは 2〜3 個のまま（区切りボタン）。接続先は今のエージェントの分だけ出る。エージェント × 接続先で伸びる（サンプルの登録 3 件で 5 行）。区切りボタンには収まらず一覧になる。
アカウントとの排他アカウントの節は残り、互換の接続先では選べない見た目＋一文で理由を示す。公式の Claude Code を選んだときだけアカウントの節が出る。理由は書かないで済むが、節が出たり消えたりする。
既存の規則との揃いprocway の面（エージェント → 接続先 → モデル）と同じ並び。エージェントの切り替え（docs/backend-handoff.md: 常に新しいセッション）と混ざる。同じエージェント内の切り替えは引き継げるので、見た目と挙動がずれる。
チップ・右クリックチップ「OpenRouter · glm-4.6」。右クリックは「接続先（次のターン）」の子メニューが 1 つ増える。チップは同じ。右クリックはエージェントの子メニューに全部並ぶ。

見てほしいところ

  • 左右の面はどちらも操作できます。B で「Claude Code」と「Claude Code — OpenRouter」を行き来すると、アカウントの節が出たり消えたりします。
  • 推奨は A。理由: エージェントの一覧が伸びないこと、エージェントの切り替え（新しいセッションになる）と接続先の切り替え（同じセッションで続く）を分けて見せられること、procway で使ってきた並びと同じこと。
  • B の良いところ: 1 回で選べる。接続先が 1〜2 件なら短い。
