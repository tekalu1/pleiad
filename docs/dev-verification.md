# 開発中の確かめ方

テスト・画面・デスクトップ版を手元で確かめる手順と、踏んだ落とし穴。作業の規則は `AGENTS.md` にある。日付は確かめた日。

## テスト

- `tests/lint-design.mjs --strict`（`npm test` の design-lint）は、CSS の `background` に `--surface-*`・`--fill-*`、`color` に `--ink-*` 以外を許さない。`--line-*` は svg の `fill`/`stroke`、`linear-gradient(var(--line-x),var(--line-x))` の背景、border だけ。独自の変数（`--rail-line` など）を経由した色も族が判らず落ちる。普段と触れたときで色を替えるときは、規則ごとに `--surface-*` / `--ink-*` を書くか、`opacity` で濃さを替える（2026-09-30、会話の地図）。単体の確認は `node tests/lint-design.mjs web/tokens.css <css> --strict`。
- 設定のページ（左のメニューの項目）を足すときは、`web/onboarding.mjs` の `pages` の配列に加えて、同じファイルの `$('<名前>Tab').onclick = () => page('<名>')` の行も足す。配列だけだと札は出るが、押しても（`.click()` でも）ページが切り替わらない（2026-10-01、コンピューターの操作の節）。`hostCapabilities` に項目を足すと、返り値を `deepEqual` で比べる `tests/unit/file-actions.mjs` の 2 か所の期待値も変わる。
- `web/client.mjs` の `onEvent` などに新しい部品（`setupXxx` が返すオブジェクト）の呼び出しを足したら、関数を切り出して `vm` で動かすテスト（`tests/unit/session-stream.mjs` など。`vm.createContext` で探す）の文脈にも身代わりを足す。足さないと全件のときに `ReferenceError: xxx is not defined` で落ちる（2026-10-03、`mobileNotify`・`notifySettings`。git の動きの `refreshGit`・`gitPanel` でも同じことが起きた）。
- e2e（実際の LLM）でツールの結果を判定に使うときは、出来事の `tool.result` の `text` が 2000 字で切られている（`core/backends/shared.mjs` の `MAX_RESULT_CHARS`）。MCP の結果は `{"content":[{"type":"text","text":"…"}]}` の中にエスケープした JSON として入る。`list_ops` のような長い一覧は後ろが見えず、`JSON.parse` も通らない。短い結果（`code` など）だけを文字列で見て、一覧にあることは、その操作を呼べたこととサーバーの状態で確かめる（2026-10-03、`tests/e2e/control-human-only.mjs`）。
- 全件で 1 本だけ落ちたら、まず単独で再実行する（2026-10-01、`server-shell` は全件のときだけ落ち、単独では 3 回とも通った）。
- CI（4 vCPU）でだけ時々落ちる本は、手元（32 コア）でただ負荷をかけても再現しない。テストの node と忙しく回るだけの node を同じ 2 コアに縛る（`ProcessorAffinity = 3`。子のシェル・サーバーにも引き継がれる）と再現する。2026-10-03 は、試す本と busy loop の node 6 本を 2 コアに固定して 3 回流し、`shell-runs`（止める前に 400ms の上限で終わる）と `server-setting-approval-delegated`（120ms 決め打ちの待ち）が 3 回とも落ちた（`temporary/scripts/ci-flaky-pinned.ps1`）。1 コアに 8 本は厳しすぎて、CI で出ていない本まで落ちる。直し方は、決め打ちの時間を条件がそろうまでの待ちにする・試す動き（止める）と別の動き（上限）を同じ短い上限で走らせない。製品が `where` などの子プロセスを短い上限で打ち切っているなら、混んだ利用者の PC でも同じことが起きるので製品を直す（`findNodeOnPath`。負荷の下で `where node` は 16 回中 12 回 5 秒を超えた）。
  - 2 コアに縛っても、後片付けの `fs.rm` の `ENOTEMPTY`（消している最中に別の書き込みが一時ファイルを作る）は、テストのままでは 15 回流しても再現しなかった。疑う流れだけを小さなスクリプトに抜き出し、`io`（`createAgentTasks` などが受け取る `fs`）を Proxy で包んで「close の後に始まった書き込み」を数えると、はっきり出る（2026-10-03、修正前の main で 200 回中 199 回。`temporary/scripts/silence-close-probe.mjs`）。
  - 同じ縛り方で `agent-tasks` を何回も流すと、`tests/unit/agent-tasks.mjs` の「12 件と追加指示 25 件を 4 秒で終える」待ちが、3 回目あたりから修正前の main でも timeout になる（2026-10-03）。CI では出ていないので、この本がここで落ちても変更のせいとはみなさない。
- **並列と分割（`node tests/run.mjs`・`npm test -- …`）**。既定は従来どおり、同じプロセスで全 suite を登録の順に 1 本ずつ。
  - `--jobs N`（1〜32）: 子プロセスの worker を N 本起こし、重い suite から順に、空いた worker へ 1 本ずつ渡す。同じプロセスの中で suite を並行させない。worker は suite の出力を suite ごとにまとめて、終わった順に出す。`npm test -- --jobs 2 markdown` のように名前の絞り込みとも組める（`--jobs 2` の `2` は suite 名にならない）。
  - `--shard k/N`: 時間の重み（`tests/suite-weights.json`。suite 名 → ms。無い suite は `defaultMs`）で LPT（重い順に、いちばん軽い箱へ）して N 分割した k 番目だけを走らせる。決定的で、全 suite がちょうど 1 つの shard に入る。CI のジョブ分けに使う（各ジョブが同じ分け方を見ていることは、`--timings` の `planHash` で突き合わせられる）。名前の絞り込みと組むと、絞った集合を分割する。
  - `--timings <path>`: suite ごとの状態（pass / fail / skip / error / crash）・時間・判定数・skip の理由・worker・開始終了と、worker ごとの結果を JSON で書く（重みの更新にも使う: `suites[].ms` を `tests/suite-weights.json` へ写す）。`--list [--json]` は走らせずに、選ばれた suite と重みだけを出す（shard の中身を見る）。
  - 登録（`tests/run.mjs` の一覧）は走る前に検査する: ファイル・名前の重複、`export const name` が読めない、ファイルが無い、`tests/unit` にあるのに登録していない、は終了コード 2 で何も走らせない。suite を足すときは一覧に `'./unit/<名前>.mjs',` を 1 行足す。名前は実際の `export const name` と突き合わせる（違えばその suite が失敗）。重みの無い新しい suite も、必ずどれかの shard・worker で走る。引数が不正なときも 2。
  - 隔離: worker は親の `AGENT_HOST_DATA` を受け取らず、worker ごとに自分の一時ディレクトリを作って終わりに消す（`tests/lib/run-worker.mjs`）。実行元の制御用の環境変数は run.mjs と worker が外す。ポートは各 suite が 0 で取る。
  - 異常系は黙って成功にしない: worker が suite の途中で死ぬ（exit・kill）と、その suite だけが失敗（`crash`。終了コードと直近の出力が残る）になり、残りは走る。登録した suite が走らなかった・二重に走った場合は「ランナー: 実行の整合」が失敗する。回収は、起こした worker と、その子孫（worker が起こしたサーバー・`core/host-shell.mjs` や `core/hook-adapter.mjs` の detached のシェルなど）だけ。ほかの node には触れない（`tests/lib/process-reap.mjs`）。見つけ方は、POSIX が worker のプロセスグループと、worker ごとの環境変数の印 `PLEIAD_TEST_WORKER_TAG`（Linux は `/proc/<pid>/environ`。グループを抜けた孫も見つかる。`/proc` の無い macOS はグループ内だけ）、Windows が PowerShell で読むプロセス表の親子の鎖（pid の使い回し・止める直前の再確認つき。プロセス表が読めなければ失敗にする）。親が外から止められると、worker は自分と子孫を止めて終わる。**保証しない範囲**: Windows の Git Bash 経由で起こした孫は、worker が suite の途中で死ぬ・親が強制終了されると、仲介のプロセスが先に消えて親子の鎖が切れ、残りうる（suite が正常に終わる・ランナーが SIGINT/SIGTERM で止められる場合は止まる）。
  - `tests/unit/runner-contract.mjs` が、引数・登録・分割・`--jobs 1` と `--jobs 2` の結果の一致・異常系・隔離・回収を、`tests/lib/runner-fixtures/` の小さな試験用 suite で確かめる。
- 「テストの後に本体の git の分けた作業場所が増えていない」（`tests/run.mjs` の見張り）は、全件の間に**本物の Pleiad が同じリポジトリで委譲の子に作った作業場所**（`D:/dev/pleiad.pleiad/ply-*`）でも落ちる。見張りは、その間に増えたものを、そのとき走っていたテストのせいにする。見分け方: 挙がった作業場所とブランチがもう無い（`git worktree list` に無い・`git log pleiad/ply-xxxx` が unknown revision）、または落ちた本が作業場所と関係ない。その本を `node tests/run.mjs <名前>` で単独で走らせ、前後で `git worktree list` の数が変わらなければテストのせいではない（2026-10-03、並行する会話がある間の全件で 4 本、単独では全部通った）。
- Pleiad の会話のシェルから `npm test` を流しても、`PLEIAD_CONTROL_URL`・`PLEIAD_CONTROL_TOKEN`・`PLY_CONTROL_*`・`AGENT_BROWSER_*`・`AGENT_HOST_PORT`・`AGENT_HOST_BIND`・`AGENT_HOST_TOKEN` は、`tests/lib/test-env.mjs`（run.mjs の最初の import。worker も同じ）が外すので、`env -u …` は要らない（以前は、会話のシェルへ渡された `PLEIAD_CONTROL_TOKEN` がテストの中の Claude の env に引き継がれて `control-delivery` の「Claude: controlRuntime が無ければ…」が落ちた。2026-10-04）。外した名前は実行の頭に出る。`AGENT_HOST_CLAUDE_BIN` などの利用者が試験用に渡す上書きは外さない。テストが子プロセスへ明示して渡す値には影響しない。
- 本物の Codex の app-server の JSON-RPC（通知の順・item の中身）を見るときは、stdio を 1 行ずつファイルに書きながら本物の `codex.exe` へ中継する node スクリプトを `AGENT_HOST_CODEX_BIN='node "<スクリプト>"'` に渡し、別ポート・別のデータ置き場でサーバーを立てる。理由: Pleiad の出来事からは turn/started や item の形が見えず、fake-codex は本物の形を仮に出しているだけ。2026-09-28 は、`thread/shellCommand` の直後の `turn/start` が同じターンに入って返答が消えることを、これで突き止めた（`temporary/scripts/shell-real/codex-tap.mjs`）。記録には会話の本文が載るので、測り終えたら消す。
- コンピューターの操作（`ply_computer`）を本物の Claude・agy で確かめるときは、実画面に触れないよう `AGENT_HOST_COMPUTER_DRIVER=fake` を付け、別ポート・別のデータ置き場・一時の作業場所（cwd）でサーバーを立てて、ws-client から「screenshot を 1 回だけ呼んで中身を答えて」と送る（2026-10-01 に haiku と gemini-3.8-flash で 1 回ずつ。名前・表示・画像を読めるかが分かる）。終わったら、agy は `~/.gemini/antigravity-cli/` の `annotations/<id>.pbtxt`・`brain/<id>`・`conversations/<id>.db`・`presence/<id>.lock`、Claude は `~/.claude/projects/<作業場所を - にした名前>` を消す。理由: どちらも本物の会話の一覧に残る。

## fake で画面を出す

起動の基本は `AGENTS.md`（別ポート・別のデータ置き場の fake）。

- fake は初回「未ログイン」で最初の案内が開き、作業ディレクトリも空のため、そのまま送った会話は「未送信」に残り、送信済みが前提の操作（タイトル生成など）が押せない。案内の「ログイン」→「あとで」→ 入力欄で作業ディレクトリを指定してから送る。スクリプトで撮るときは、案内のダイアログが `#settings` への click を奪う（設定のメニューも隠れる）ので、先に `#closeOnboarding` を押す（2026-10-03）。
- fake の応答は即座に返り、処理中の表示が一瞬で消える。見るときはページ上で `WebSocket.prototype.send` を包み、対象コマンド（例: `suggestTitle`）の送信を数秒遅らせる。

## 重さと動きを測る

- 実データの写しは `node scripts/copy-data-dir.mjs <temporary/ の下の写し先> [--light] [--keep-tasks]` で作る（手でフォルダーをコピーしない。注意は `AGENTS.md`）。元（既定は `AGENT_HOST_DATA` か `~/.agent-host`）は読むだけで、DB は読み取り専用の接続で `VACUUM INTO` して写す（動いているサーバーの DB のファイルをそのままコピーすると、WAL に未反映の分が `-wal` に残って壊れた写しになる）。**`remote/`（同じホストの鍵で中継へつなぎ、本物の接続を追い出す）と `*-secrets.json`・`control.json` は写さない**。委譲の続きを走らせないため、写しの `agent_tasks` は既定で空にする（`--keep-tasks` で残す）。`--light` は会話の本文（`conversations/`）・`handoff-*.json`・`uploads/` などを写さない（移行や 1 回の更新の時間を測るだけなら要らない）。写しの DB を直に見るなら `tests/lib/data-store.mjs` の `readSessions`・`readAgentTasks`・`readUsage`（読み取り専用の接続）。形式 1 の置き場を元にすると、写しは起動のときに DB へ移る（その時間と大きさを測れる。2026-10-03 の実データ: JSON 4 つ計 35.4MB → `pleiad.db` 25.5MB、移行 0.9 秒、会話 1,112 件の読み込み 0.13 秒、1 回の更新は中央値 0.02〜0.6 ミリ秒。[ADR 0115](adr/0115-records-in-sqlite.md)）。時間は Playwright の CDP で測る。`Emulation.setCPUThrottlingRate`（4 倍でスマホの目安）をかけ、`Profiler.start` / `stop` で取ったサンプルを関数ごとに self・inclusive で集計すると、原因の関数まで出る。2026-09-26 はこれで、描画のたびに `layoutBranchSpine` が強制レイアウトを起こしているのを突き止めた。スクリプトは `temporary/scripts/session-open-*.mjs`。
- 送信量（`running` など委譲のタスクが載るもの）を実データで測るときは、写しの DB の `agent_tasks` を空にしない（空にすると `running` が空になる。2026-10-03 のリモートの重さの主因は、これが 1 回 3.26MB あったこと）。代わりに写しの DB の中で `notification` が `pending`・`delivering` のタスクの行を `sent` にし、`AGENT_HOST_CLAUDE_BIN`・`AGENT_HOST_CODEX_BIN`・`AGENT_HOST_AGY_BIN` を存在しないパスにして立てる（委譲の通知を送り直さず、エージェントも起動しない。履歴の読み出しは `~/.claude` などを読むだけなので動く）。実データの写しのサーバーは起動に約 2 分かかり、`tests/lib/server.mjs` の `startServer` の既定（中継の組み立ての `chain.mjs` では 60 秒）では起動待ちで落ちるので `timeoutMs` を伸ばす。中継の線で大きな出来事が詰まらせる量は、大きな応答を 4 秒ごとに要求しながら小さなコマンド（`prefs`）を 250ms ごとに送り、その応答時間で見る。スクリプトは `temporary/scripts/remote-perf/`（`copy-real.mjs` 写し・`cmd-sizes.mjs` コマンドごとの大きさ・`phone.mjs` スマホの画面・`chain.mjs` と `relay-client.mjs` 中継）、結果は `temporary/reports/remote-slow-running-broadcast.md`。
- 夜の記憶の整理（`core/memory/learn.mjs`）が実データでどれだけ読むかは、写しの置き場でモデルを呼ばずに走らせて測る。`AGENT_HOST_DATA=<写し>` を付けて node のスクリプトから `core/store.mjs`（import の時点で置き場を決めるので、環境変数は先に）・`core/backends/claude.mjs` の `backend`・チャンネルと記憶のサービスを読み込み、`createMemoryLearner` に `ask`（候補の代わりに `{"memories":[]}` を返し、渡った発言を数える）と `listBackends: () => [claude]` の host を渡して `runIfDue()` を呼ぶ。サーバーを立てると learner が本物のモデルを呼び、本物の `~/.claude` に会話を作るので立てない。`prepareMessages` は async（await を忘れると配列でなく Promise が返る）。2026-10-04 の実データ: Claude の会話 861 本・人の発言約 2,700（14 日で約 2,100）、全部を 1 回読むのに 35 秒。直す前の作りは束ごとに全部を読み直し、500 秒で読み終わらなかった。直した後は 40 束・200 件を 35 秒（[ADR 0118](adr/0118-memory-strength-and-learner-runs.md)）。スクリプトは `temporary/scripts/learn-probe-run.mjs`・`learn-probe-count.mjs`。
- スクロールの重さは、開いて落ち着かせた長い会話の `#log` へ 900px のホイールを 40ms 間隔で送り、CDP の `Performance.getMetrics` の `LayoutCount`・`LayoutDuration` とフレーム間隔の p95 で比べる（`temporary/scripts/scroll-jank-measure.mjs`）。開く時間を縮める変更はスクロールを重くすることがあるので、両方を測る。2026-09-27 は、開く時間のために入れた `content-visibility:auto` の仮の高さ（160px）と実寸の差で、スクロール中にレイアウトが繰り返されていた。

- `content-visibility:auto` の行が自分で実寸に描き直される範囲を測るなら、行の中身を仮の高さと同じ高さにして `contentvisibilityautostatechange`（`e.skipped`）を数え、そのときの位置で距離を出す。Chromium（headless shell 1234）で見える範囲の上下、窓の高さの 1.3〜1.5 倍だった。`checkVisibility({contentVisibilityAuto:true})` は遠い行でも true を返し当てにならない。また `content-visibility:auto` の行が多いと、強制レイアウト（`.height-ready` の付け外し）1 回ごとに未確定の行の数に比例した style 再計算が走る（2000 行・CPU 4 倍で 1 行の確定でも約 77ms）ので、確定は 1 回のレイアウトにまとめる（`web/history-heights.mjs`）。
- 会話の位置の測定は、狭い窓（1280 幅など）に加えて `#log` が約 1,736px を超える広い窓（2560 幅）でも行う。会話の列は `max-width:860px` で左に寄るので、`#log` の中央の点で当てる処理は広い窓でだけ列の外に落ちる。2026-09-28 は、これで広い窓の利用者だけが、長い会話を開くと末尾から上へずれていた（1280 幅では再現しなかった）。
- スマホの重さは、PC の CPU 等倍ではほとんど見えない（2000 発言でも開くのに 3.6 秒）。390×844・`isMobile` の Chromium で CPU を 4〜6 倍に絞り、中継の経路（遅延と帯域を入れたプロキシ越しの `relay/server.mjs` と端末プロキシ）も通して測る。2026-09-29 に使った種・段階ごとの測定・中継の組み立ては `temporary/scripts/mobile-perf/`（`seed.mjs`・`measure.mjs`・`chain.mjs`）、結果は `temporary/reports/mobile-long-session-perf.md`。遅延を入れるプロキシは、塊ごとに `setTimeout` すると Windows のタイマーの丸めで順序が入れ替わり、Noise の復号に失敗して線が切れる。届いた順の列にして先頭から書く。
- 分岐のような rAF で動かすアニメーションを数十 ms 刻みで撮って比べるときは、ページを遅くする。Playwright のスクリーンショットは 1 枚に約 80ms かかり、等速では 780ms の動きが 10 枚ほどしか撮れない。`addInitScript` で `performance.now`・`requestAnimationFrame`（コールバックに遅くした時刻を渡す）・`setTimeout` を K 倍遅くし、CSS の遷移と WAAPI は CDP の `Animation.setPlaybackRate`（1/K）で遅くする。毎フレームの数値（ノードの `left`・`--reveal`・`stroke-dashoffset` など）も記録し、各段の始まり（`data-phase` が変わった時刻）からの時間で並べると、2 つの実装の差が px で出る。2026-09-29 に K=8 で、LP の分岐の模型とアプリを比べた（`temporary/scripts/lp-branch/` の `slow.js`・`probe.js`・`app-capture.mjs`・`compare.mjs`）。
- 放置時の自動圧縮（idle）が得になっているかは、`temporary/scripts/` の `idle-compaction-events.mjs`・`idle-compaction-ttl.mjs`（それぞれ `temporary/reports/` に JSON を出す）を流してから、`idle-compaction-after-150k.mjs` で損益を出す（読み取りのみ。前回の結果は `temporary/reports/idle-compaction-effect.md`・`idle-compaction-after-150k.md`）。圧縮の要求は Claude の transcript に残らないので、費用は `usage.json` の圧縮ターンの記録から取る（2026-09-28 以降の記録はターンごとの値。それより前は会話の累計なので、前のターンとの差を取る）。戻ったときの実際の大きさは、境界の後の最初の要求の読み・書きで見る。圧縮されなかった放置の理由は `idle-missed-why.mjs` で、直前のターンが通知（委譲の完了など）で始まっていないかを見る。予約は利用者が始めたターンの後にしか作られない（2026-09-30 時点）。
