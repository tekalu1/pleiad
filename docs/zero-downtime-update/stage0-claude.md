# 無停止の更新・段階 0（実測）: Claude の付け直し

管理 issue: #54。保持役（ターンの保持役）に CLI の stdio を持たせ、入れ替わった新しいサーバーが同じ CLI に SDK の `query` を作り直して付け直す、という設計の Claude 側の前提を、実際に動かして確かめた記録。

- 印: **【確認】** = この調べで動かして確かめた。**【推測】** = 動かしていない見込み。
- LLM は `haiku`・ツール 1 つ・短い指示で呼んだ（1 ターン約 0.01〜0.02 USD。全体で 60〜80 ターン）。

| `@anthropic-ai/claude-agent-sdk` | 0.3.288（`claudeCodeVersion` は 2.1.288） |

## 方法

`scripts/zero-downtime/claude/` に置いた。ユーザーの Pleiad・データ置き場は使っていない（`core/` も読み込んでいない）。

- `holder.mjs`: 保持役の最小の模型。名前付きパイプで受け、CLI を起動し、stdin を握り、stdout を行ごとに通番を付けて記録する。親が居なくても読み続ける。CLI からの `control_request` のうち親がまだ答えていないものの控えを持ち、`attach` で（選べば）渡し直す
- `parent.mjs`: 親の役。SDK の `query` を `spawnClaudeCodeProcess` で保持役につなぐ（偽の `SpawnedProcess`）。`first` は保持役に CLI を起動させ、`second` は既存の子に付けて新しい `query`（= 2 回目の `initialize`）を作る
- `run.mjs`: 親を**別プロセスで起動し、`taskkill /F` で捨てる**（保持役と CLI は残す）。項目 1〜3・5 の場面を動かす
- `s4-http-outage.mjs`: 項目 4。`core/mcp-bridge.mjs` と同じ形（POST だけ・JSON の応答・通知は 202・GET は 405・Bearer）の最小の HTTP MCP サーバーを立て、ポートを閉じる・接続を切る・応答を止める
- `s5-unread-stdout.mjs`: 項目 5 の stdout の詰まり。保持役を介さず CLI を素の stdio で起動する

動かし方は各ファイルの先頭のコメントにある（例 `node scripts/zero-downtime/claude/run.mjs perm gap=2000`）。記録は `%TEMP%` の下に出る。

### 1. 承認待ちの最中に付け直す

`Bash` の `touch` を使わせ（既定の承認モードでは聞かれる）、`can_use_tool` が CLI から来て親が答えないまま親を殺し、同じ stdio に新しい `query` を作った。

- 新しい `canUseTool` が**付け直しの約 70〜90 ms 後**に、**元と同じ `requestId`・`toolUseID`** で呼ばれた。許可を返すと CLI がツールを実行し、ターンは `result` まで完了した【確認】
- 経路は CLI の `initialize` の応答の `pending_permission_requests`（保持役は控えを渡していない）。保持役の控えの再配送を足しても、記録を最初から流し直しても、`canUseTool` は **1 回しか呼ばれなかった**（SDK 側で同じ要求が 1 つにまとまる）【確認】
- 親が居ない時間を 0.3 秒・60 秒・**300 秒**にしても同じ（保持役が stdin を閉じなければ CLI は承認の依頼を持ち続け、時間切れにならない）【確認】
- 2.1.288 でも同じ【確認】
- 旧サーバーが親を静かに終える場合の確認（対照）: 旧サーバーが SDK の `query` を `close()` すると、SDK が stdin を閉じて kill する。**そのまま転送すると CLI が終わり、承認待ちのツールは実行されずにターンが終わる**。保持役への `write` / `end` / `kill` を転送しなくしてから `close()` すると、CLI は無事で、新しい親が承認を受け取れた【確認】

### 2. ツール実行中・応答の生成中の付け直し

応答の生成中は、約 125〜175 行・80〜90 KB の stream-json（`includePartialMessages` あり。1〜300 の数字を書かせたもの）の途中で親を殺した（10・60・120 イベント目）。ツール実行中は、12 秒の `sleep` の最中に殺し、2 秒後・18 秒後に付けた（18 秒後はツールが親の居ない間に終わっている）。

- 新しい親へ流す位置を「殺した親が**アプリのループで処理し終えた**最後の行の次」にすると、保持役が持つ全部の行（uuid を持つもの）に対し、取りこぼし 0・重複 0 だった（応答の生成 3 回・ツール 2 回）【確認】
- 殺す前に親が SDK の stdout へ流した行は、その時点でアプリが全部処理していた（この規模では流した位置と処理した位置が一致した）【確認】。**途中で殺されて SDK の内部に残る行が出うる場合の差は測れていない**【推測】
- 重複が出たのは、親の殺し方が非同期で、親の最後の位置の記録が実際より遅れたときだけ（スクリプトの初期の版で 14 行。殺し方を同期にして消えた）。記録が遅れると重複は出るが、取りこぼしは出ない。再生は uuid で冪等にする前提
- 付け直した `query` は、ターンの途中（`message_start` の無い `content_block_delta` など）から流れてきた `stream_event` をそのまま処理し、`result` まで正しく完了した。アプリの正規化がターンの頭から要るなら、ターンの頭（印）から流し直す必要がある
- ツールが親の居ない間に終わっても、`tool_result` と `result` は保持役に溜まり、付け直しで受け取れた【確認】
- SDK は `system/session_state_changed` を、利用者に渡さず内部で消費する。再生で流し直しても害は無い
- 付け直した `query` で `interrupt()` が効いた（ツール実行中。応答 10 ms、`result` は `error_during_execution`）【確認】

### 3. hooks と in-process MCP

`createSdkMcpServer` の `host` サーバー（ツール `ping`）と、全ツールの `PreToolUse` / `PostToolUse` のコールバックを、最初の `query` と付け直した `query` の両方に同じ形で渡した。

- 待機中（ターンの合間）に付け直し、新しい指示を送ると、**付け直した親の `host.ping` のハンドラーが呼ばれ、hooks のコールバックも発火した**【確認】。2 回目の `initialize` で SDK が `sdkMcpServers` と hooks の id を送り直し、CLI はそれを使う。2.1.288 でも同じ
- **in-process MCP の呼び出し（`mcp_message`）の最中に付け直す**:
  - 保持役が「答えていない `control_request`」を新しい親へ渡し直すと、新しい親のハンドラーが呼ばれ（付け直しの約 20〜120 ms 後）、ターンが完了した【確認】
  - 渡し直さないと、**CLI は要求を再送せず、45 秒待っても終わらない**（止まったまま）【確認】。MCP の呼び出しには保持役の控えの再配送が要る
  - 旧サーバーのハンドラーが終わる前に捨てられると、同じ呼び出しが新しい親で**もう一度**走る（少なくとも 1 回の配送）。`host` の `fork` などは 2 度走ると困る【推測。呼び出しが 2 度走ることまでは確認、`fork` では試していない】
- **hooks のコールバックの最中に付け直す**: 保持役が控えを渡し直しても渡さなくても、CLI が自分で、その呼び出しを次のエラーで打ち切る。**そのツール呼び出しは実行されない**:
  `PreToolUse:Bash hook error: The SDK host reconnected before its PreToolUse hook answered, so this tool call was not executed. No one denied it; retry the same tool call.`
  モデルが同じ呼び出しを自分でやり直し（今回は 2 回目で成功）、ターンは完了した。渡し直された `hook_callback` は新しい親で走ったが、CLI は答えを使わなかった（無駄になる）【確認。2.1.284・2.1.288 とも】
- つまり付け直しで失うのは「その時に走っていた hooks のコールバック 1 回分とそのツール呼び出し 1 回」で、モデルのやり直しに頼ることになる

### 4. HTTP MCP が数秒つながらない

`mcp-bridge.mjs` と同じ形の MCP サーバーを `type: "http"` で CLI に渡し、ツールを 1 回呼ばせた。

| 場面 | CLI のふるまい |
|---|---|
| ポートを閉じておき（`ECONNREFUSED`）、呼び出しの 1〜20 秒後に同じポートを開き直す | **呼び出しは即座に `ECONNREFUSED` のツールエラー**で返る（待たない、再試行もしない）。MCP の状態は `connected` のまま。開き直した後の次の呼び出しは成功した。1・3・20 秒で同じ |
| 呼び出しの最中に接続を切り、ポートを 3・10 秒閉じる（`ECONNRESET`） | **即座に `ECONNRESET` のツールエラー**。`connected` のまま。開き直した後の次の呼び出しは成功 |
| 接続は受けるが `tools/call` の応答を 3・10・30 秒止める | **待って成功する**（30 秒まで確認。時間切れにならない）。次の呼び出しも成功 |

- MCP サーバーごと外される（以後使えない）ことは、20 秒までのどの場面でも起きなかった【確認】。`mcpServerStatus` を 0.5 秒ごとに見て、状態は `connected` のままだった
- 耐える秒数: 閉じたポートに対しては**待たずに失敗する**ので、「耐える」のではなくツール 1 回が失敗で済む。接続を握って待たせる形（段階 4）なら 30 秒までは成功する
- CLI を**つながらない間に新しく起動した**ときの MCP の状態（起動時の接続が失敗した扱いになり、後で戻るか）は測っていない【未確認】

### 5. 親が居ない間・stdout が読まれない間

- 親が居ない間、保持役が stdin を閉じず stdout を読み続ける限り、CLI は生き続けた（0.3 秒・18 秒・60 秒・300 秒。承認待ちのまま 300 秒でも、付け直して許可すると続いた）【確認】
- CLI の stdout を**誰も読まない**と、約 20 KB の応答を 3 回返すまで（約 60 KB）は問題なく、12 回（約 240 KB）返したあたりから **CLI のループが止まった**。読まない 12〜20 秒のあいだ、`Bash` ツールは実行されなかった。読み始めると、溜まった応答（最大 400 回・約 8 MB）が全部戻り、ターンも完了した（応答の欠落なし）【確認。止まる量は 60〜240 KB の間までしか絞れていない】
- 数字を 300 行書かせただけのターンでも約 80〜90 KB の出力があった（`includePartialMessages` あり）。長いターンはこの量を超えるので、**保持役は親の有無にかかわらず stdout を読み続けて溜める必要がある**。保持役のイベントループが長く止まることも避ける

## 設計（design.md）を変える点

1. **付け直しの前に旧サーバーが「手を離す」順序を書く**（§4.4 Claude・§5）。旧サーバーが SDK の `query` を閉じる・中断すると、SDK が stdin の終了と kill を送り、CLI（と承認待ちのツール）が終わる【確認：対照】。`spawnClaudeCodeProcess` が返す偽の `SpawnedProcess` は、`detach` の後は `write`・`end`・`kill` を保持役へ転送しない
2. **保持役の `spawn` / `attach` を、SDK が最初の stdin を書く前に送る**。SDK は `spawnClaudeCodeProcess` の戻り値を受け取るとすぐ `initialize` を書く。後から送ると、その `initialize` は保持役で（子がまだ無いため）捨てられ、CLI は hooks・SDK MCP を知らないまま始まる（このスクリプトの最初の版で起きた。ターンは動くが hooks・MCP が効かない）
3. **控えの再配送は `can_use_tool` では要らない**（§4.1 の答えていない依頼の控え）。`pending_permission_requests` で足りる。再配送しても `canUseTool` は 1 回に畳まれるので害は無いが、要らない。**`mcp_message` は必須**（再配送しないと CLI が止まる）。**`hook_callback` は再配送しない**（CLI が自分で打ち切るので無駄）。`elicitation`・`request_user_dialog`・`oauth_token_refresh` など他の種類は未確認
4. **引き継ぎの前に、走っている hooks のコールバックと `mcp_message` のハンドラーが終わるのを（上限つきで）待つ**。hooks は、捨てるとそのツール呼び出しが 1 回失敗する（モデルがやり直す）。`mcp_message` は、旧サーバーが答える前に捨てると新しいサーバーで二重に走りうる。待てない分は上のとおり失うか二重に走る
5. **流し直す位置はアプリが処理し終えた最後の行**（§4.5）。取りこぼしは出ない。記録の位置が遅れると重複が出るので、再生は uuid で冪等にする。途中の `stream_event` だけを受けても SDK は壊れないが、正規化がターンの頭を要るなら印から流す
6. **保持役は stdout を常に読む**（§4.1）。読まれないと CLI が止まる
7. **in-process の `host` MCP は HTTP に移さなくてもよい**（§4.4「`host` MCP は HTTP に移す」）。付け直しの 2 回目の `initialize` で、in-process の MCP も hooks も効く。しかも in-process の `mcp_message` は、サーバーが居ない間も CLI が答えを待つ（再配送があれば完了する）。HTTP に移すと、つながらない間の呼び出しは**待たずに失敗する**ので、移すなら段階 4 の「待ち受けを保持役が持ち、新しいサーバーが立つまで接続を待たせる」を足したうえでないと、今より悪くなる。移すかは「二重に走る可能性（in-process）」と「その場の失敗（HTTP）」の比べ
8. **段階 4（待ち受けを保持役が持つ）の根拠が出た**（§4.6・§5）。HTTP MCP の口が数秒つながらないと、その間の呼び出しは即座にツールのエラーになる（MCP は外されず、後の呼び出しは成功）。接続を握って待たせれば、30 秒までは成功する。段階 1〜3 では「引き継ぎの 1 秒前後に当たった呼び出し 1 回が失敗しうる」を受け入れるか、旧サーバーが進行中の HTTP の呼び出しが終わるまで待ってから口を閉じる
9. **`VERIFIED` の版**: 付け直しを確かめた CLI の版は 2.1.284・2.1.288（`core/backend-shape-diagnostics.mjs` の `VERIFIED` と `docs/multi-backend.md`「外部エージェントの版」に足す候補）
