# issue を登録する

このリポジトリは公開されている。issue の本文・タイトル・コメントは誰でも読める。

## いつ作るか

- 利用者が登録を頼んだときだけ作る。自分で課題に気づいただけなら、一覧（タイトルとラベル）を示して確かめてから作る。
- 1 つの課題に 1 つの issue。関連する小さな課題は 1 つにまとめてよい（見出しで分ける）。

## 手順

1. **重複を確かめる。** `gh issue list --state all --search "<語>"` で、同じ課題が無いかを見る。近いものがあれば、新しく作らずにコメントするか、本文の「関連」に `#<番号>` を書く。
2. **根拠を集める。** 参照するのは、リポジトリにあるものだけにする: `docs/` の節、`docs/adr/` の番号、コードのファイル（`web/…`、`core/…`）。`temporary/` の下（コミットしない）は読者が開けないので書かない。
3. **本文を書く。** `temporary/issues/<nn>-<題>.md` に Write tool で書く（heredoc は `'` を含む長文で壊れるため使わない）。形は下の「本文の型」。
4. **伏せ漏れを調べる。** 下の「入れないもの」を読み直し、次を実行する。当たった行はすべて開いて確かめ、個人のものなら書き換える。

   ```bash
   grep -rnE '(^|[^A-Za-z])[A-Za-z]:[\\/]|/Users/|/home/[a-z]|@[a-z0-9-]+\.[a-z]|sk-[A-Za-z0-9]|ghp_|github_pat_|xox[bp]-|AKIA|AIza|acct-|Bearer ' temporary/issues/
   ```

   正規表現で見つからない固有名（利用者の名前・アカウントの表示名・社名・顧客名・非公開のリポジトリ名）は、会話で出てきたものを思い出して目で探す。
5. **参照先が実在するか確かめる。** 本文に書いたファイル・ADR の番号を `git ls-files` や `ls docs/adr` で見る（ADR の番号は並行作業で変わることがある）。
6. **登録する。**

   ```bash
   gh issue create --title "<領域>：<内容>" --label "<ラベル>" --body-file temporary/issues/<nn>-<題>.md
   ```

   ラベルは `gh label list` にあるものから選ぶ（よく使うもの: `bug`・`enhancement`・`accessibility`・`documentation`・`remote`）。
7. **報告する。** 作った issue の番号と URL、タイトルを利用者に一覧で返す。

## 入れないもの

- 手元の絶対パス（ドライブ名から始まるパス、ユーザー名を含むホームのパス）。書くなら `~`・`%TEMP%`・`<作業場所>` のように一般化するか、リポジトリの中の相対パスにする。
- 利用者の名前・メールアドレス・アカウント名やその ID（Claude のアカウントの表示名、`acct-…` など）。
- API キー・トークン・パスワード（伏せ字にした一部も書かない）。
- 社名・顧客名・非公開のリポジトリ名・非公開のプロジェクト名。
- 利用者の使用量・料金など、手元のアカウントの実際の数字。
- 実データの画面のスクリーンショット（個人の会話・パスが写る）。載せるなら fake バックエンドで撮ったものだけ。
- 会話の中の内部のやりとり（「子エージェントに任せた」など）。課題そのものだけを書く。

## 本文の型

```markdown
## 概要

何が起きるか・何が足りないかを 1〜3 文で。どの版からか（例: 0.1.0-beta.44 から）。

## 現状

- 事実を箇条書きで。推測は「原因（推測）」の節に分けて書き、推測だと分かるようにする。

## 期待する挙動

- どうなってほしいか。やり方が複数あれば案として並べる。
  （不具合でなく作業のときは「やりたいこと」）

## 関連

- #<番号>、ADR <番号>、`docs/<ファイル>` の節、コードのファイル
```

- タイトルは「<領域>：<内容>」（例: 「コンテキストの設定：…」「委譲の振り分け：…」）。既存の issue の書き方に合わせる。
- 再現の手順があるときは、版・OS・バックエンド・モデルを書く（手元のパスやアカウントは書かない）。
- 文は短く、画面の文言は実際の表示どおりに「」で書く。
